## Build and Development Commands

```bash
npm install            # Install dependencies
npm run dev            # Start Vite dev server (port 5173)
npm run build          # Full production build (Te Araroa sync + climate + trails + TS compile + Vite)
npm run build:trails   # Build trail pages from data/trails/
npm run build:mobile-trails # Build the app's bundled trail JSON (mobile/assets/trails/)
npm run publish:trail-data  # Publish mobile trail JSON + catalog to R2 (--dry-run, --check, --all, --force, --remove <id>)
npm run sync:te-araroa # Copy the Te Araroa route out of the te-araroa-data package
npm run fetch:climate  # Fetch climate data for trail locations
npm run fetch:access <trail-id> # Find where off-route waypoints are walked to from (OSM + DEM → access.json)
npm run fetch:elevation # Fetch elevation data
npm run build:tiles    # Build map tiles
npm run fetch:fonts    # Fetch font glyphs for map labels
npm test               # Run all tests with Vitest
npm test -- --watch    # Watch mode
npm run lint           # Run ESLint (src/ and scripts/)
npm run preview        # Preview production build locally
```

## Git Workflow

**Rebase and merge is the only merge method allowed in this repo.** A PR lands on `main` as a linear run of its own commits, so a branch must never contain a merge commit. To pick up `main` or resolve conflicts, rebase the branch onto `origin/main` (`git rebase origin/main`, resolve each commit, then push with `--force-with-lease`) — never `git merge main` into the branch. A merge commit on a branch cannot be rebase-merged and has to be unpicked afterwards, which is far more work than rebasing in the first place.

## Architecture Overview

**Trail Maps** is a TypeScript web application for displaying Australian long-distance hiking trails with interactive maps, elevation profiles, and waypoint data. The repo also contains **Tracknotes**, the companion Expo/React Native mobile app (`mobile/` — see Mobile App section).

### Core Library (`src/lib/`)

Shared processing modules (used by both web and mobile):
- `distance.ts` - Haversine distance calculations
- `gpx-parser.ts` - Parse GPX XML into structured data; `parseGpx(xml, adapter?, limits?)` is platform-neutral (see XML adapters below) and parses coordinates strictly (throws instead of plotting 0,0)
- `xml-adapter.ts` - Minimal XML node interface (`querySelectorAll`/`querySelector`/`childElement`/`getAttribute`/`textContent`, tag selectors only) + the DOMParser adapter. `querySelector` searches every descendant, so a field that must be the element's *own* (`<wpt>`'s `<name>`/`<type>`, not its `<link>`'s) goes through `childElement`
- `xml-adapter-fxp.ts` - fast-xml-parser adapter (the React Native path — Hermes has no DOMParser)
- `gpx-optimizer.ts` - Track simplification (Douglas-Peucker), elevation spike removal/smoothing, elevation stats
- `track-simplify.ts` - Target-point-count simplification + coordinate truncation (the mobile point budget)
- `track-classification.ts` - Classify main/alternate/side-trip/**terminus** tracks. A `terminus` (`terminusPatterns`, default `['^Terminus:', '\\bTerminus\\b']`, collected into `terminusTracks`) is an *alternative trail end*: it branches off the main line at one end and its other end is deliberately free, 10-31 km off the route (the CDT's Chief Mountain, Columbus and Antelope Wells). It is matched **after** alternate and side trip, so a track a trail already names `Alternate: …` keeps that class. Several main tracks are normally chained by `combineTracksGeographically`, which orders them by proximity and bridges every join. A trail whose `trackClassification.stretches` is set instead uses `concatenateStretches`, which keeps the file's order and records any join wider than `minGapMeters` as a **route break** — somewhere the walking route genuinely stops and resumes (a ferry, an unbridged river). Opt-in per trail: turning it on for a file whose tracks are not in walking order would silently reorder the route
- `route-breaks.ts` - Reading those breaks back out for anything that draws the route (`splitAtRouteBreaks`, `routeBreakCrossings`). Breaks leave `track.points` a single flat array — every other consumer wants one ladder of cumulative distance — so only line-drawing code needs this. Used by both maps: the web viewer's `drawMainRoute` and mobile's `buildTrailLine` (a MultiLineString, one stretch per line). Anything that draws or climbs *part* of the route uses the other two: `sliceAcrossRouteBreaks` (the plan page's day lines, mobile custom-route spans) and `routeBreakStarts`, the index set the elevation helpers take so a ferry's landing-to-landing height difference is never climbed
- `waypoint-classifier.ts` - Classify waypoint types (town, hut, water, etc.). Five tiers: CalTopo folder → `KNOWN_TOWNS` → name prefix (`C:`/`WT:`…, delimiter required) → `KEYWORD_RULES` word matching → `waypoint`. The keyword tier is opt-in (`inferFromKeywords`) and is **on for user imports, off for the curated build** — guessing types for curated trails would churn `public/data/generated/*.json` for no gain
- `map-glyphs.ts` / `waypoint-glyphs.ts` - The one map icon set for both platforms. `map-glyphs.ts` holds the shapes (`MAP_GLYPHS`: 96x96 SVG bodies inked with `currentColor`; no imports and erasable TypeScript only, because `mobile/scripts/build-map-icons.mjs` loads it straight through Node's type stripping to rasterise `mobile/assets/map-icons/*.png`). `waypoint-glyphs.ts` maps a waypoint type (`waypointGlyph`, turn-offs via `baseWaypointType`) or OSM POI category (`poiGlyph`) to a glyph, and the glyph to one of six colour families (`waypointFamily`/`poiFamily`: water, camp, town, shelter, hazard, neutral). The family is derived from the glyph, never listed per type, so an alias cannot get the water drop on a grey ring. Mobile resolves a family to its `waypoint*` theme tokens (`elevation/waypoint-category.ts`, which also drives the list filter chips); the web inlines `glyphSvg` (`src/web/trails/waypoint-icons.ts`) and colours it with the `--wp-*` custom properties in `styles.css`. No emoji anywhere a waypoint type is drawn
- `waypoint-taxonomy.ts` - The waypoint type vocabulary (`WAYPOINT_TYPES`, `WAYPOINT_TYPE_LABELS`, `waypointTypeLabel`) and the water/resupply family predicates (`isWaterWaypoint`, `isResupplyWaypoint`, `matchesWaypointFamily`). These predicates are the single home of rules that used to be duplicated across `water-carry-calculator`, `day-calculator` and `resupply-calculator`; they also accept the type aliases real-world GPX uses (`spring`, `supermarket`, …), which our own classifier never emits
- `trail-types.ts` - Shared `ProcessedTrail` / `TrackData` / `EnrichedWaypoint` / `RouteVariant` / `TrailConfig` — the shape of `public/data/generated/{id}.json`. `RouteVariant.type` is `'alternate' | 'side-trip' | 'terminus'`; **termini live in `sideTrips`**, not in an array of their own — every consumer of that list already means "routes that leave the trail and do not come back", so one array keeps the map lines, camera bounds, datasheet, reversal, mobile slimmer and handoff parser working unchanged, and anything that must tell them apart reads `type === 'terminus'`. A terminus has exactly one junction (`startDistance`, at `points[0]`) and never an `endDistance`
- `trail-ingest.ts` - `buildTrail(gpx, options)`: the whole GPX → `ProcessedTrail` pipeline (route selection, cumulative distance, display simplification, waypoint enrichment, variant junctions, off-trail split), with hooks for the build script's file-system/registry concerns. `track.displayPoints` aims at `DEFAULT_TARGET_DISPLAY_POINTS` (3,000) but `calculateAdaptiveTolerance` is capped at `MAX_TOLERANCE_METERS` (25 m), so a long trail overshoots that target rather than losing the shape of its line — the CDT keeps ~21,000 display points instead of drawing as straight chords beside its full-resolution alternates. A route break adds neither distance nor climb, is simplified around rather than across, and is published as `track.breaks`. **Waypoint km must stay on the track's own scale**: `enrichWaypoints`/`calculateSegmentStats` take the break indices and skip the same legs, or waypoints drift past the end of the trail they are measured along. **Variants read forwards**: `findVariantJunctions`/`attachVariantsToParents` turn a variant round (points reversed, ascent/descent swapped) when its source track was drawn against the trail, so `points[0]` is always the branch point at `startDistance`. Variant waypoint km and a child alternate's km along its parent both count from `points[0]`, so never swap the junction pair without reversing the points. **Off-route places**: a waypoint is attached to the route point nearest it in a straight line, unless `options.waypointAccess` (the build's `data/trails/<dir>/access.json`, by waypoint id) gives a junction found over OSM — then it is attached there, keeps its own position, and gets the walk in as `offTrailKm`, `offTrailAscentM`/`offTrailDescentM` (climb walking in), `accessMode: 'foot'` and, for an `osm` entry, the way itself as `offTrailPath` (`[lat, lon]` junction → place, only ever drawn: the web viewer and plan page dot it while the place's popup is open — the plan page also for as long as the place is a stop — through `src/web/trails/access-path.ts`; the phone's map after a marker tap or a "Show on map" from the waypoint screen or a Today, Day or Stops row (`features/guide/ShowOnMap.tsx`). GPX imports and community copies never carry it: GPX has no `tn:` field for it, and `community-checks` drops it — `docs/gpx-import.md` says so; a `.tracknotes.json` handoff keeps it, `trail-handoff`'s `readAccessPath`) (`matchAtJunctions`/`restoreJunctionPositions`). An entry is ignored, with a warning, when the place is beyond the match radius (a stale entry must never pull an off-trail place onto the route) or its junction is over 100 m from the route line (re-run `fetch-access`)
- `gpx-import.ts` - `importGpx(xmlText, options)`: runtime import for user-supplied GPX (elevation cleaning on, `u_`/`uw_` synthetic ids, `ImportReport`). The user-facing spec of the pipeline is `docs/gpx-import.md` — keep it in step with behaviour changes here and in `trail-ingest.ts`. It is rendered into the site as `how-import-works.html` at build time (the `gpx-import-doc` plugin in `vite.config.ts`)
- `elevation-backfill.ts` - Open-Elevation backfill for GPX without `<ele>` (`backfillElevation` batches of 100, ≤2000 samples interpolated by distance; `applyElevation` re-derives ascent/waypoint stats via `recomputeTrailElevation`); `trailHasElevation`/`trailElevationIsUsable` drive the "distance-only estimate" labels
- `contribution-licence.ts` - The licence line under everything a hiker makes public (CC0 + the terms of service, `contributionLicenceLine`) and the published `TERMS_URL`/`PRIVACY_POLICY_URL` (`public/terms.html`, `public/privacy.html`, drafted from `docs/terms-of-service.md` / `docs/privacy-policy.md`). The phone's comment composer and waypoint form ("Everyone") show it; a web form that posts publicly should too
- `community-types.ts` - Wire contract for **community routes** (spec: `plans/community-routes.md`): `c_` ids (`isCommunityRouteId`), statuses `unverified`/`verified`/`hidden`/`removed`, `CommunityRouteSummary`/`CommunityRouteDetail` (`hiddenReason` for the owner/admin of a hidden route; `statusNote` admin-only), the AI review shape, report reasons, `COMMUNITY_LIMITS`
- `user-waypoints.ts` - **Hiker waypoints**: places a hiker adds to a trail on the phone, `private` (SQLite only, never sent) or `shared` (the comments API, pulled by every phone on that trail — the missing water source or shop). One shape (`UserWaypoint`), `hw_<uuid>` ids (`isUserWaypointId`; the comments API takes comments on a shared one, and only while the server holds it on that trail), the offered types (`USER_WAYPOINT_TYPES`, a subset of `WAYPOINT_TYPES` the calculators already understand), `USER_WAYPOINT_LIMITS`, and `checkUserWaypointInput`, run by the form and again by the worker. `placeUserWaypoints` merges them into a trail *as stored* (before direction): each lands at the km of the nearest point on the main route (`placeOnTrack`, which is `position-on-trail`'s `snapToTrail` — the GPS snap — so a waypoint and a fix at one spot read the same km), the curated waypoint after it gets its arriving leg re-measured, one further than `onRouteMetres` (500 m, `buildTrail`'s match radius) of a water/campsite/hut/resupply/food/accommodation/town type is placed as a turn-off (`<type>-access` with the straight-line `offTrailKm`) so the water and resupply calculators never count a place down a side valley as on the route, and it carries a `userWaypoint` field (`userWaypointInfo`) that marks it apart. Another hiker's shared pin (`isOtherHikersWaypoint`: not `mine`) counts like any other place — its water shortens a carry — and the phone's list and waypoint screen say who reported it and when ("Reported by Jo · 12 Oct", `hikerReportLine` in `features/guide/waypoint-detail.ts`), so the hiker judges it; no hedging or advice is added to that line. They never enter the build, `data/waypoint-ids.json` or `public/data/generated/*.json`
- `community-checks.ts` - `runCommunityChecks(trail, {name, description, gpxText?})`: the automatic checks for a shared community route — shape, length, points, distance-consistency, speed, elevation, gaps, metadata, waypoints. Run by the clients before upload and again by the worker, whose result counts. It never trusts its input. Coordinates, elevations, names, text and waypoint `trackIndex` are validated and kept; a `trackIndex` whose point is beyond `buildTrail`'s match radius of the waypoint (500 m route, 200 m variant) is re-placed as an import would place it (nearest point in range, else off-trail). Everything derived is rebuilt from that geometry the way `buildTrail` builds an import: point `dist`, length, `displayPoints` (Douglas-Peucker, budgeted, stride fallback), climb (3 m hysteresis), waypoint km/legs/climb, off-trail `distanceFromTrail`, and variant length, climb, junctions and `parent`. A variant must start within 500 m of the route or an attached alternate. Route breaks, POIs, `cumAscent`/`cumDescent`, timestamps, climate and the client's direction labels are dropped. The client's own km survive only for `distance-consistency`. The result is returned as `trail`, with `stats` for the row (`waypointCount` counts main, off-trail and variant waypoints). `speed` reads the raw GPX through `gpxMovingSpeedKmh` (a string scan, null under 10 timed points) and passes with a note when there is none. O(n log n) on real tracks; messages are plain English for the person sharing. OSM POI density is deliberately not a check — it varies by trail
- `trail-regions.ts` - Countries (ISO alpha-2) and their state/region codes, `LENGTH_BANDS`, and `matchesFilter`/`sortTrails`/`groupTrails` (Country → State, first state wins, "Other" last). Shared by the web landing page, the app's My Guides and the community forms. `trail.json` carries `country`, `states` (route order) and an optional `featured`; `scripts/trail-regions-data.test.ts` enforces them. The web and mobile `index.json` and the R2 trail catalog carry them, the per-trail mobile JSON does not (`stripListOnlyConfig`), so a list-only edit never moves a trail's md5 or triggers an over-the-air download
- `region-detect.ts` / `region-shapes.ts` - Which country and states a route is in, offline: `detectRegion(points)` samples 256 points against Natural Earth outlines of every country and state in `trail-regions.ts`, plus the unlisted countries bordering them (`other`: a route in Lesotho or Andorra is LS or AD, never pulled into its neighbour). `region-shapes.ts` is generated by `npm run build:region-shapes`: land borders are simplified once for both neighbours (~500 m, so a point near one is in exactly one shape), coastlines to ~5-10 km (a point just off one takes the nearest shape within 30 km), small islands kept outside the Arctic. It returns the majority country, the states in route order (each holding ≥ 2 % of the samples), the majority `state`, and `seen` — every country and state any sample is in. It prefills the region on both community share forms (the hiker can change it; the phone only prefills a listed country), and `checkCommunityRegion` in `community-checks.ts` is the worker's `region` check, which warns only when the chosen country or state holds none of the samples — the hiker's choice is always stored as given. Every bundled trail detects as its `trail.json` `country`/`states` (`region-detect.test.ts`)
- `trail-handoff.ts` - `<slug>.tracknotes.json` web → mobile handoff format (`wrapTrailForHandoff`, strict `parseHandoffJson`)
- `poi-display.ts` - The platform-neutral half of showing OSM POIs, shared by the web viewer and the app: category labels, `poiDisplayName`, `summarisePoiTags` (+ the `safeHttpUrl`/`safeTelUrl` guards every POI link must pass), `slimPoi` (what `build-mobile-trails.ts` and the mobile import store write), the `PoiFilterState` shape and its normaliser, `visiblePois`/`countPoisByCategory` (both skip `duplicateOf`), `poisBetween` (a km span, sorted), `interleavePoisByDistance`, `mirrorPoiDistances`, the slash-free `poiRouteKey` (`type-id`) that names a POI in an Expo Router param, `poiCommentId` (`osm_<type>_<id>`, the id a POI's comments are filed under in the comments API, apart from `w_`/`hw_`) and `poiNoteUrl` (OSM's new-note page with its marker on the POI). `src/web/trails/trail-pois-ui.ts` re-exports it and keeps only the HTML/`localStorage` half
- `elevation-axis.ts` - `eleBounds`: an elevation profile's default y-axis, 0 m (or a below-sea-level low point) to just above the track's high point, never fitted to its low point. Shared by the phone's elevation pane (`features/elevation/geometry.ts` re-exports it) and both web profiles (trail page, plan page), so the same climb looks the same on each. `eleAxis` is the web's drawn axis over those bounds: nice tick steps, the top raised to the next line so the high point is never above the last label
- `text-links.ts` - `splitTextLinks`: free text → plain/link segments (`kind` `url`/`email`/`phone`). URLs go through `safeHttpUrl` (http(s) only), emails become `mailto:`, phone numbers `tel:` through `safeTelUrl`. A phone number needs 8-15 digits and a separator, a leading `+` or a `Tel:`/`Phone:` label, so OSM ids, coordinates, dates and `0800-1700` ranges in descriptions stay plain. Waypoint descriptions carry bare URLs (Shikoku's henro.org pages), inn emails and phone numbers; the web viewer renders them through `linkifyText` (`src/web/linkify-text.ts`, kept out of `web-utils` so the landing page does not load `poi-display`) and the app's waypoint detail screen with `mobile/src/features/guide/LinkifiedText.tsx`, which is selectable (long-press to copy) and opens a tapped link in the browser, mail app or dialler
- `access-routing.ts` - Where an off-route place is walked to from: `buildWalkNetwork` (OSM ways → graph joined at shared nodes, split into ≤ 25 m edges) and `findAccess`, a shortest-path search from the place (the ways within 60 m of the nearest one, reached cross-country at 1.5× cost; only if none of those leads to the route, any way within 300 m — without that, a road the route follows 200 m away across a river beat the place's own lane; and never straight to the route itself from more than 150 m — 500 m over ground no steeper than 1 in 5 — which drew Rainbow Falls 225 m down a cliff) to the first node within 35 m of the route line, never across a route break. The cost is the *round trip* by Naismith's rule (a metre of climb = 8.3 m of flat): with one junction the route is walked whole either way, so the round trip is all that differs between junctions, and it climbs every height difference along the path once, which makes edges symmetric. Shikoku's Maekawa Campground is why: 1.4 km from the top of the Temple 20 climb in a straight line, 2.8 km of flat road from the bottom. Returns the junction and its km, the walk's length, climb in (3 m hysteresis), cross-country part and path. Pure; the caller supplies ways and heights (`scripts/fetch-access.ts`)
- `poi-noise.ts` / `poi-dedup.ts` / `poi-urban.ts` - The build/import-time passes between a raw `pois.json` and the shipped `pois` array: drop category-wide noise, flag POIs that duplicate a curated waypoint, thin city stretches (see `pois.json` under Trail Data)
- `position-on-trail.ts` - `snapToTrail(lat, lon, points, hintIndex?, breakStarts?)`: the one projection of a position onto a track — the nearest *segment* (not vertex; bundled tracks are thinned to ~900 m spacing on the CDT), a windowed scan around the hint with an exact full scan as fallback, route breaks never snapped across, antimeridian-safe. Returns the segment's start `index`, `currentKm` and `offTrailMeters`; `isOffTrail` / `OFF_TRAIL_THRESHOLD_M` (50 m). Used by the phone's GPS position (`useLocation`, `use-plan-route`), custom routes, waypoint detail and hiker-waypoint placement (`user-waypoints.ts`)
- `point-index.ts` - Uniform-grid nearest-point lookup (`buildPointIndex`, `PointIndex.nearest`) in raw degree space, for answering "which track point is under the cursor?" without scanning a 20,000-point display copy on every mousemove. Platform-neutral, so the mobile map can reuse it; the web trail viewer rebuilds its index wherever `displayPoints` is set
- `types.ts` - TypeScript interfaces
- `plan-types.ts` - Plan data types shared with mobile. `PlanDocument` (id-keyed stops with `nights`, `note`, `booked`; `PLAN_LIMITS`) is the one plan shape: the wire body of `PUT /v1/plans/:id`, mobile's `plans.document_json`, the web `localStorage` value and the shared-plan payload. `PlanState` is legacy, read only by the web migration
- `plan-editor.ts` - The pure plan editor both platforms drive (spec: `plans/day-planner.md`): `toggleStop`, `replaceStopsInRange` (applying a suggestion), `setNights`/`setStopNote`/`setStopBooked`, start date and direction, `overnightCandidates`, `computePlanDays` (nights cascade into dates and `restDays`), `splitUnplannedTail` (the stretch after the last stop is "not planned yet" until it fits in a day), `servicesAtStop` over the trail's OSM POIs (1 km, `duplicateOf` included, `undefined` when the trail has no POI data), `refreshStopKms` (moves a stop to its waypoint's current km when a data update moved the place — by id, against the trail as stored, an alternate's stops against that alternate's waypoints; never onto another stop's km — run on every plan load and server copy by both planners: the phone's `GuideView`, the web `plan-viewer` init and `adoptServerPlan`, saving and syncing only a real change; never from trail data older than the plan's `dataUpdatedAt`, the newest data time any save stamped on it (`stampPlanData`/`planDataIsCurrent`) — the phone's copy's `updatedAt`, and on the web the generated JSON's `dataUpdatedAt`, which `build-trails.ts` sets to the app index's `updatedAt` while the committed app file is exactly this build's data and to the build time otherwise (`scripts/lib/web-data-time.ts`); the server refuses a stamp that is not a strict ISO time or is in the future, and clients read a far-future one as none), `migratePlanState`, `isPlanDocument`. Every editor returns a new document or the same object for a no-op; stop km stay NOBO-absolute
- `plan-alternates.ts` - Taking a trail's alternates in the day planner (spec: `plans/day-planner.md` "Alternates"). `buildPlannedRoute`/`plannedRouteTrail` splice the chosen alternates (`PlanDocument.alternates`, by name; only `type: 'alternate'` with both junctions and no `parent` — `plannableAlternates`) into the main line, giving a trail of the same shape in **route km**, so every planner calculator runs on it unchanged. The document keeps its km contract: a main-route stop is NOBO main km, a stop on an alternate carries `alternate` and the alternate's own absolute km (branch km + km along it). Both planners hold the stored document and edit a route-km view of it (`planToRoute`/`planFromRoute`, `editPlanOnRoute`); a stored stop the view cannot show is carried back unchanged when `planFromRoute` is given the stored plan, so always pass it; `setPlanAlternate` is the one edit that changes the route (drops overlapped alternates and bypassed stops, moves a stop whose waypoint id both lines share). `alternateMarkers` places the Stops list's branch/rejoin cards. One stop per place is checked per line, client and server
- `day-suggest.ts` - `suggestDays`: the N best alternative plans for the next K nights from a km, over caller-supplied candidates. It runs a k-best DP ranked by mean squared, range-scaled deviation from distance/ascent/hours targets, and a final walk out to the range end is held to maximums only. The criteria are the hiker's: `assertSearchable` refuses a set with no maximum rather than capping it. Both planners use it: the phone's Next days card and the web plan page's "Plan the next few days" section
- `plan-suggest.ts` - What both planners put around `day-suggest`, so they cannot drift:
  - the hiker's inputs (`SuggestPrefs`: mode, days, options, distance/ascent/hours ranges), their pace-derived starting values (`defaultSuggestPrefs`) and shape check (`isSuggestPrefs`);
  - the two modes as criteria (`suggestionCriteria`);
  - where a suggestion starts (`suggestionStart`: location, else last stop, else section start);
  - `applySuggestedPlan`;
  - the hour bands: `planWindowHours`, `planFloorHours`, and `finalDayMaxHours`, the most hours a plan's last day may take before it is "not planned yet".
- `track-geometry.ts` - Nearest-point lookup and elevation gain/loss between km positions. `calculateElevationBetween` (and `buildTimeIndex` in `day-calculator.ts`) take an optional `breakStarts` set — pass `routeBreakStarts(track.breaks, 'points' | 'displayPoints')` for whichever array you hand them, or a trail with route breaks climbs the gap between landings. When the points carry `cumAscent`/`cumDescent` (`annotateCumulativeElevation`, written into the mobile assets before thinning) both read the difference of the two ends instead of walking the steps between them, and `breakStarts` is not consulted — the break step was already left out of the sums. Summing a thinned track's own steps reported 65-86% of its real climb
- `day-calculator.ts` - Hiking time estimation and day splitting; `buildTimeIndex` reads the points' `cumAscent`/`cumDescent` when they carry them, so it keeps matching `calculateElevationBetween` to the metre on thinned and full-resolution tracks alike. **Stops off the route are walked to**: `placeWalk(waypoint)` is the walk to a place (`offTrailKm` with its climb in, `offTrailAscentM`/`offTrailDescentM`) or null — on the route, a turn-off, or a ride (`hitch`/`shuttle`/`boat`, or an unsaid distance over `WALKED_WHEN_UNSAID_MAX_KM`, 5 km; `resupply-plan` re-exports it). A `PlanStopInput` carrying `walk` adds the walk in to the day that ends there and the walk back out (climb and descent swapped) to the next: `distanceKm`, `ascentM`, `descentM` and `estimatedHours` include it, and the day carries `offTrailKm` and `walkIn`/`walkOut` (absent when it stays on the route; `startKm`/`endKm` stay route km). `computePlanDays` looks each stop's walk up by `waypointId` through `stopWalk`, which gives none to a stop no longer at its waypoint's km (saved before a data update moved the place: that day already walks the old way there). `day-suggest` counts a candidate's `walk` and `fromWalk` (the last stop's walk out, via `SuggestStart.waypointId` and `stopWalk`) the same way, keeping the shortest walk where places share a junction km, and the phone's Stops-list legs (`plan-stops.stopLegs`, walks looked up in the trail's waypoints, not the candidates shown) and Today rows (`today-plan.todayRows`) add up to the same day. All four add walks through `addPlaceWalks`, the one home of the out/in sum
- `resupply-calculator.ts` - Town resupply point calculations (incl. food carry weight; the long-carry days and grams per day are required, never defaulted); which waypoints count comes from `isResupplyWaypoint` in `waypoint-taxonomy.ts`
- `water-carry-calculator.ts` - Water carry distance calculations (the dry-stretch km is the hiker's and required); which waypoints count comes from `isWaterWaypoint` in `waypoint-taxonomy.ts`. A carry is measured as walked: the route km between sources plus the walk back out of the source it starts at and in to the one it ends at (`placeWalk`; the gap's `fromOffTrailKm`/`toOffTrailKm`), and a source another one beats for walking (at the same km nearer the route, or on the route a short way along from a tap down a side valley) is dropped rather than listed as a carry nobody walks
- `resupply-plan.ts` - Resupply *planning*: `resupplyCandidates` (the main route's waypoints plus every town a **side trip** leads to — on the side trip, or an off-route town within 1 km of its far end — offered at the junction with the side trip's length as `offTrailKm`, `accessMode: 'foot'` and its climb in `accessRoute`; call sites pass `resupplyCandidates(trail)`, never `trail.waypoints`) → `listResupplyOptions` (every resupply-family waypoint, grouped by the turn-off you leave the route at) → `resolveResupplyStops` (the ticked ids → stops; `undefined` = every option) → `computeResupplyLegs` (real ascent, Naismith hours, days, food per leg; **requires** `dailyHours` and `baseKmh` and throws rather than defaulting them). Each stop carries its `access` (`StopAccess`: the longest *walk* among its ticked places, else the longest ride), and a leg walks out of the stop it starts at and into the one it ends at: `distanceKm` stays trail km, `offTrailWalkKm`/`walkedKm` add the walk (in the hours, days and food), and `rides` lists the hitch/shuttle/boat km — and a distance whose way the data does not give (all of Te Araroa's) past `WALKED_WHEN_UNSAID_MAX_KM` (5 km; shorter unsaid ones are walked) — which are reported, never timed. `resupply-display`'s `legDistanceText`/`legRidesText`/`stopAccessText` are the shared wording ("52.3 km + 4.0 km off trail") → `summariseResupplyLegs`. Also `allResupplyOptionIds` and `plannedResupplyIds` (a ticked option plus the point on the route that serves it — the km the food has to reach — and *only* that point: at the CDT's Monarch Pass, ticking Salida must never plan Poncha Springs, the other town on the same hitch), which is what every mobile "planned" surface highlights
- `resupply-display.ts` - The platform-neutral text of a resupply option: `firstSentence` (abbreviation-aware), `accessSummary` and `resupplySummaryText`, each taking the caller's distance/weight formatter so the web (metric) and the phone (unit preference) share one set of words

**XML adapters:** GPX parsing is injected, not hard-wired, so one parser serves three runtimes. `parseGpx` defaults to `DOMParser` (web); build scripts pass `jsdomXmlAdapter` (`scripts/lib/xml-adapter-jsdom.ts` — jsdom must never reach `src/lib`); mobile passes `fxpXmlAdapter` (`src/lib/xml-adapter-fxp.ts`). A parity test (`src/lib/xml-adapter.test.ts`) asserts the fast-xml-parser and DOMParser backends produce deep-equal `GpxData` for every fixture.

**Ingestion is shared, not forked:** `scripts/build-trails.ts` and `importGpx` both call `buildTrail`, so a GPX file produces the same trail in the build, on the web and on the phone. The build script keeps only what needs a file system: CalTopo GeoJSON, the CSV waypoint fallback, climate, curated descriptions, the `data/waypoint-ids.json` registry, and HTML generation — each passed in as a hook. Any change to `trail-ingest.ts` must leave `public/data/generated/*.json` byte-identical unless the change is intentional.

**Shared calculators:** `track-geometry.ts`, `day-calculator.ts`, `resupply-calculator.ts`, `resupply-plan.ts`, `resupply-display.ts` and `water-carry-calculator.ts` are the single implementations used by both web and mobile. Mobile imports them via the `@lib` alias (Metro `watchFolders` + tsconfig paths + Jest `moduleNameMapper`). Parameter types are structural (e.g. `PlanWaypoint`, `PlanStopInput`) so each platform's own trail/waypoint/stop shapes are accepted without conversion. On mobile the Plan screen edits a saved `PlanDocument` through `@lib/plan-editor` (SQLite `plans`, `state/plans-store.ts`); nothing writes stops on its own. The Next days card (`features/plan/NextDaysCard.tsx` + `plan-suggest.ts`, over `@lib/day-suggest`) offers ranked alternatives for the next few nights from the GPS km or the last stop, by hours & pace or by distance/climb/hours ranges (per-trail inputs in `plan-inputs-store` `suggest`). Applying one replaces only the stops inside its window. Pace and daily hours stay per trail in `plan-inputs-store.ts` (device-local, not part of the document — a shared plan should not say how fast its author walks); the resupply selection is `PlanDocument.resupplyStops`, edited through `setResupplyStops`, with a legacy `plan-inputs-store` selection read only while the document has none. The adapters live in `mobile/src/features/plan/plan-adapters.ts`. Pace presets (`Pace`, `PACE_KMH`) live in `plan-types.ts` so the two platforms cannot drift.

### Build Scripts (`scripts/`)

- `build-trails.ts` - Generates static trail pages + `public/data/generated/*.json` from GPX/JSON data; the geometry work lives in `@lib/trail-ingest` (`buildTrail`) — this script only supplies the file-system pieces (config, CalTopo GeoJSON, CSV fallback, climate, curated descriptions, waypoint-id registry) and writes the output
- `build-mobile-trails.ts` - Builds mobile-optimized trail JSON (reduced points, truncated precision). A trail with route breaks is simplified one stretch at a time, so Douglas-Peucker cannot drop a break's boundary points and cut the corner across the water; `index` is re-anchored to the result, `displayIndex` is re-anchored the same way, because `displayPoints` is thinned here too: the web copy is no longer a fixed ~3,000 points (see `trail-ingest.ts`'s tolerance ceiling), so the phone clamps it to the same `TARGET_POINTS` budget as `points` — a line no coarser than the array it already ships, and no finer. Every point of both arrays also gets `cumAscent`/`cumDescent`, measured on the full-resolution track *before* thinning (`annotateCumulativeElevation`, skipping the step into each break) and rounded to whole metres: thinning keeps the shape of the line, not its ups and downs, so without them the phone's plans, ETAs and route stats under-counted climb by 14-35%. `processTrail` is exported and `main()` guarded so this is testable. `index.json` records each file's `md5`/`bytes`, and a trail's `updatedAt`/`dataVersion` move only when its md5 changes (the previous index is read back), because `updatedAt` is what the app orders over-the-air copies by
- `build-contours-australia.ts` - Builds contour PMTiles for the contour tile worker
- **Contour zoom tiers** (`tile-pipeline.ts`: `CONTOUR_TIERS`, `contourTierLayer`, `contourTierFilter`, `contourTippecanoeArgs`, `renameContourTiers`) - which elevations appear at which zoom (100 m lines from z9, 50 m from z10, 20 m from z12, 10 m from z13), shared by the Australia build, the world build, the per-trail offline packs and the experiment harness. tippecanoe's `-L {"file","layer"}` object has **no `minzoom` key**: every archive built before 2026-10 passed one and had it silently ignored, so each z9–z12 tile carried every 10 m contour, blew its byte budget, and `--drop-smallest-as-needed` (whose threshold applies to a whole zoom level, set by its densest tile) emptied it — Mt Sonder's live world z9 tile kept one 100 m line — while the Australia archive's `--minimum-detail=4` quantised what survived onto a 16×16 grid: the "jagged when zoomed out" contours. So each tier is read as its own tippecanoe layer (`contour_z9`…), a `-j` feature filter admits it from its minzoom (`$zoom`), and tile-join `-R` folds the layers back into the one served `contour` layer (`renameContourTiers`) — the world build's batch and shard joins do it in passing, the other builds add one tile-join pass. The tippecanoe quality bundle (`CONTOUR_TIPPECANOE_DEFAULTS`: simplification 2 at z9–14, minimum detail 7, 1 MB tiles) is defined once there too; the per-trail packs used to tile with the pre-decision-gate flags. Re-tiering is a tippecanoe-only change: `--merge-only` re-runs, no cell rebuild

- `fetch-pois.ts` - Fetches OSM POIs along each trail corridor via the shared `gpx-tools` library (`npm run fetch:pois [trail-id]`). Reads track geometry from `public/data/generated/{id}.json` (so `build:trails` must have run) and writes the results to `data/trails/<dir>/pois.json` — in the repo, where a rebuild cannot wipe them. `--endpoint <url>` / `OVERPASS_ENDPOINT` and `--timeout <seconds>` pick the Overpass instance; mirrors come and go, so try them in turn: `overpass.private.coffee` served the Australian trails (2026-09-08, `--timeout 120`), but by 2026-09-30 it timed out from a cloud session, where `overpass-api.de` reset the connection and `overpass.kumi.systems` timed out too. What answered there was `--endpoint https://maps.mail.ru/osm/tools/overpass/api/interpreter`, which drops any query past about 60 s, so it wants small cheap ones: `--max-vertices 60 --timeout 55` (or 150/120 for a lighter trail). On 2026-10-06 `overpass.private.coffee` answered again (`--timeout 120`, Shikoku in one 182 s query), but its data lagged: the same day `maps.mail.ru` (`--max-vertices 60 --timeout 55`) returned a 2026-09-21 survey of central Tokushima that it lacked

Nearby places share one Overpass query (boxes ≤ 10 km across: bigger ones over Japanese cities drew HTTP 500s), and every answer is cached in the gitignored `data/osm-ways-cache/`, so a change to the routing re-runs from disk (`--refresh` re-downloads). Failed queries get three more passes a minute apart; `--only <ids>` re-runs what a run lost. A waypoint the build merged near-duplicates into (`dedupeWaypoints`, its `mergedIds`) gives every twin the same entry, or the merge would keep the twin without one on the next build; on such a trail a second fetch-and-build round can still move a survivor, so re-run until `fetch-access` changes nothing. Writes `data/trails/<dir>/access.json` and prints each place's km before → after; a failed query keeps the place's previous entry and exits 1, so re-run until it exits 0. ### Trail Data (`data/trails/`)

Each trail has its own directory containing:
- `*.gpx` - Original GPX track data
- `trail.json` - Trail metadata and waypoints
- `climate.json` - Climate data for locations along the trail
- `pois.json` - Optional OpenStreetMap points of interest along the trail, written by `fetch-pois.ts` and folded into the generated JSON's `pois` array by `build-trails.ts`. POIs are kept **separate from waypoints**: they are never merged into `waypoints` and never enter `data/waypoint-ids.json`. Shape: `{ source, attribution, fetchedAt, searchRadiusKm, endpoint, rejected, pois }`, where `pois` holds everything fetched (sorted by `distanceAlongTrail`, then key) and `rejected` is a hand-edited list of `<type>/<id>` keys the build drops. A re-fetch carries `rejected` over unchanged, so review work survives a refresh. The file is the raw fetch: three build-time passes sit between it and the shipped JSON — `@lib/poi-noise` drops category-wide noise (bus stops other than walkers' shuttles, picnic shelters and pergolas, hospitals tagged `emergency=no`, help phones on motorways and in road tunnels), `@lib/poi-dedup` flags POIs a curated waypoint already covers — matched against every waypoint the trail has (`dedupCandidates`: main route, off-trail, alternates, side trips and termini), and against a generic `poi`-typed one only when the two are within 10 m with the same name, and `@lib/poi-urban` thins cities: where POIs run over 15 per km of trail (seeded there, grown out through suburbs at half that, at least 40 POIs) it keeps only the first and last of each category, anything flagged `duplicateOf`, and "anchors" — supermarkets, convenience stores (Japan's resupply: the Shikoku henro's konbini), outdoor shops, post offices, campgrounds, huts, hospitals with `emergency=yes`, stations, ferry terminals — one per kind per 2 km, branded first. That took Te Araroa from 8,790 shipped POIs to about 2,100 (Auckland 3,166 → 50), and also thins Albany (Bibbulmun), Albury (Hume and Hovell) and Jackson (CDT); small trail towns stay whole. All three run at build/import time, never at fetch time, so changing a rule is a rebuild rather than another slow Overpass run. A trail can add rules of its own in `trail.json` `pois` (`TrailPoiConfig`): `exclude` drops OSM `key=value` tags that are no use on that trail (Shikoku drops `amenity=post_office` and `amenity=fuel`; a POI that is also `shop=convenience`/`supermarket` is kept), and `keepInCities` exempts a tag within `withinKm` of the route from city thinning (Shikoku keeps every konbini within 500 m: one per 2 km hid 19 of the 40 a pilgrim walks past in Tokushima). `build-mobile-trails.ts` ships them to the app slimmed through `@lib/poi-display` `slimPoi` (display tag keys only, rounded coordinates, no `duplicateDistanceM`). See `scripts/lib/trail-pois-file.ts`.
- `access.json` - Optional: where each off-route waypoint is walked to from, by waypoint id (`scripts/lib/trail-access-file.ts`), written by `fetch-access.ts` and applied by `build-trails.ts` with no network. `method` `osm` (found: `junction`, `junctionKm`, `offTrailKm`, climb in, the walk's `path`, and `straightLineM`/`nearestKm` — what the build did without it), `manual` (hand-written `junction` + `offTrailKm`; a re-fetch never touches it, so correct OSM here) or `none` (`reason`; nothing applied). Review a re-fetch by its diff: a `junctionKm` far from `nearestKm` is a place that moved
- `descriptions.json` - Optional curated waypoint descriptions, keyed by the stable ids in `data/waypoint-ids.json`. `build-trails.ts` applies them to the bundled trail JSON (overriding any GPX/GeoJSON text); `upload-descriptions.ts` pushes the same file to the comments API, where mobile syncs it as an override (`synced ?? bundled`). The prose is factual and non-prescriptive — it describes the place and its water, never instructs the walker or addresses them as "you". See `scripts/lib/waypoint-descriptions.ts`.

A trail may also carry `Terminus: <name>` tracks — alternative starts/finishes, declared with `trackClassification.terminusPatterns` and drawn junction-first, with a `<wpt>` of `<type>endpoint</type>` at the free end. `buildTrail` attaches the one junction at whichever end is actually nearer the route (turning the line round if the generator drew it backwards), attaches the nearby waypoints including that endpoint to the variant, and keeps the endpoint out of `offTrailWaypoints` so a place the route reaches is never also listed as a place it misses.

Te Araroa's file also carries waypoint types no other trail uses. `gap` is the "Trail ends"/"Trail resumes" pair at each route break. The **turn-offs** are points on the route at the km you leave it for a place that is somewhere else, typed `<servedType>-access` — `town-access`, `hut-access`, and so on — so one field says both what kind of place it is and that you are not there yet.

Two rules follow, both in `waypoint-taxonomy.ts`:
- `RESUPPLY_TYPES` lists `town-access`/`food-access`/`resupply-access` **one by one** rather than stripping the suffix generically. A `water-access` must never satisfy `isWaterWaypoint` — that would tell the carry calculator there is water on the route when it is down a side road, and under-reporting a dry stretch is the dangerous way to be wrong.
- `baseWaypointType()` is the fallback for every map keyed by type: `MAP[type] ?? MAP[baseWaypointType(type)] ?? FALLBACK` gives a turn-off its served type's icon, colour and chip without seven more entries per map. Use it rather than enumerating; `isAccessWaypoint()` is there for the cases where a turn-off must behave *differently* from the place (you cannot sleep at one — see `overnightWaypoints`).

Changing a bundled waypoint's `type` re-keys it in `data/waypoint-ids.json`, which matches on type + 100 m proximity: the ids churn silently and any server-side comment keyed to them is orphaned. Migrate the registry entries in the same commit. A waypoint whose exact name is on a nearby entry claims it before any proximity match (nearest pair first across the trail), so a newcomer of the same type within 100 m of an existing waypoint mints its own id instead of taking that one's; when it does, the build warns, naming the waypoints beside it (one place entered under two names looks the same), and repeats the warning at the end. It warns only on the build that mints: from then on the newcomer claims its own entry by name, so check the warning before committing the registry. A newcomer with the *same* type and name within 100 m stops the build — the registry cannot tell a second place from the first entered twice — so give two such places distinct names. So does a pair of same-name waypoints that have both moved and are each in range of the other's entry, since nearest-first could swap their ids: set the entries' coordinates in the registry by hand. An entry no waypoint matches in a build is kept but marked `retired: true`; a retired entry is reclaimed only by a waypoint of the same type, within range, with the exact same name, so a new place built near a removed one never inherits its id, comments or description.

**Te Araroa is not curated here.** Its route, waypoints and resupply points are built in [te-araroa-data](https://github.com/eamon-b/te-araroa-data), which commits its outputs; this repo takes them as a devDependency pinned by `package-lock.json`. `npm run sync:te-araroa` copies `te-araroa-sobo.gpx` out of `node_modules` into `data/trails/te_araroa/`, where it is gitignored — only `trail.json` and `climate.json` are committed. `npm run build` runs the sync first, so a fresh clone (or Vercel) builds without a manual step. `npm update te-araroa-data` takes a newer build. Do not hand-edit the GPX: it will be overwritten, and the fix belongs upstream.

**Open-data trails.** Eleven Australian trails come from open data rather than a guidebook, and each `trail.json` `dataSource` names its dataset and licence: the Great Ocean Walk and Great South West Walk from Great Trails Victoria (CC BY 4.0, waypoints included); the Overland, Three Capes and South Coast tracks from the Tasmanian LIST Transport Segments layer (CC BY 3.0 AU) with OSM waypoints; the Great North Walk, Six Foot Track, The Coast Track, Grampians Peaks Trail, Kep Track and Thorsborne Trail from OSM route relations (ODbL). Their `<ele>` is Copernicus GLO-30 sampled every 30 m and smoothed over five samples before it was written, because the build sums every delta and raw surface-model samples read forest canopy as climb (the Great South West Walk read +6,220 m raw, +3,400 m smoothed). The GPX files were generated once and are the source of truth here; the generator is not committed. Their waypoints have since been reviewed by hand (2026-10: towns and trail ends added, duplicates and non-public camps removed or retyped `poi`, names fixed), so a regeneration would lose that review — diff the waypoints against the committed file before replacing one. Where their climate locations sit off the trail's height (a river camp under a slope, a range crossing the terrain model smooths down, a coastal point on a sea cell), `climateLocations[].elevation` makes `fetch-climate.ts` correct the temperatures to that height.

### Comments API Worker: community routes (`workers/comments-api/`)

`src/community.ts` / `src/community-review.ts` (migrations `0005`, `0006`): D1 `community_routes` + `community_route_reports`. A submit re-runs `@lib/community-checks` (with the uploaded GPX as `gpxText`, for the `speed` check) and stores *its* rebuilt trail, never the client's JSON, with `config` rewritten server-side (id, name, `source: 'community'`, country/states, description, CC0 `dataSource`). The bucket has no private area (all of it is served at `PHOTOS_PUBLIC_BASE`), so private objects live at unguessable keys recorded in the row and never returned: the canonical trail JSON at `community/private/<id>/<32 random hex>.json` (`private_key`) and the optional raw GPX (≤ 5 MB) beside it as `.gpx` (`gpx_key`; a file whose head is not `<gpx` is dropped, not refused). While a route is live, a public copy of the same bytes sits at `community/v1/<id>.<md5[0..12]>.json` (`r2_key`; `max-age=300`, so an edge copy outlives a hide by minutes, not a year). An owner's edit writes new objects, keeps the public version it replaced (cached lists still name it) and purges older ones; a de-attribution purges the old public versions at once, since they name the deleted account; hiding a route (AI review, reports or admin) deletes every object under `community/v1/<id>.` and NULLs `r2_key`, so owner/admin detail of a hidden route has `trailUrl: null`; an admin restore from hidden always republishes from the private copy (if it is gone: 404 when removed meanwhile, 409 `conflict` when the row changed, else 500 `trail_missing`), and a hide re-reads the row after its purge and republishes a route a restore made live meanwhile; removal purges both prefixes. Every row change sets `updated_at` strictly later than the value it read (`stampAfter`); an owner's PATCH, an admin status change, a de-attribution and the AI review write only if `status`/`updated_at` still match the row they read — a lost race returns 409 `conflict` (PATCH, admin) or retries (de-attribution) and deletes the objects it wrote, and a stale review writes nothing (its verdict write leaves `updated_at` alone). `@lib/community-checks` rebuilds every distance and climb from the coordinates (point km, length, display points, waypoint and variant km, 3 m-hysteresis climb) and drops client route breaks, POIs and `cumAscent`/`cumDescent`, so no client-claimed distance or climb is stored. The duplicate hash is sha256 of the trail without its `config`, so a rename does not get past it (the 409 carries `existingId` only for the caller's own route; the near-duplicate warning names the other route by id); a body whose non-GPX part exceeds 4 MB + 64 KB is refused 413 `trail_too_large` before it is checked; the 10-a-day `communitySubmit` limit is spent only after the checks pass and the stored JSON measures ≤ 4 MB, `communitySubmitAttempt` (30 a day) is spent by every submit before its body is parsed, and `communityEdit` (20 a day) by every PATCH that changes something. The `claude-sonnet-5-5` review (structured output, `fallbacks: 'default'`, all route text fenced as untrusted) runs from `waitUntil` (SDK client with a 20 s timeout and 1 retry) and **fails open** — `skipped` without the `ANTHROPIC_API_KEY` secret (`wrangler secret put ANTHROPIC_API_KEY`), `failed` on an API error or refusal. The review also sees a bounded sample of waypoint descriptions, the variant names, and a sample of off-trail and variant waypoint names (≤ 200 names in all, at least 50 of them off-trail/variant when there are that many). A reject with confidence ≥ 0.8, or 3 distinct reports filed after the route's last admin status change (`status_changed_at`) by accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`; younger accounts' reports are stored but do not count), hides an *unverified* route; a verified one stays up and rises to the top of the admin queue. An owner's detail of a hidden route (`GET /v1/me/community/routes`, or `GET /v1/community/routes/:id` with their token) carries `hiddenReason` (`'review' | 'reports' | 'admin'`). It is derived from the hide's `status_note`: the review and report hides write the fixed `REVIEW_HIDE_NOTE`/`REPORTS_HIDE_NOTE`, and anything else counts as an admin hide. `statusNote` itself stays admin-only, and an admin note equal to either fixed note is refused 400 `invalid_note`. Only an admin verifies. Deleting an account de-attributes its routes (CC0) rather than removing them; `deattribute_pending` keeps that durable, and a Cron Trigger (`*/15 * * * *`, `runCommunityMaintenance` in `src/index.ts`'s `scheduled`) retries pending de-attributions and re-runs AI reviews left `pending` over 10 minutes. A submit also adds the `region` check (`checkCommunityRegion`: a warning when the coordinates are in another country or state, never a change to the hiker's choice), and a PATCH that changes the region re-runs it. A PATCH re-runs the `metadata` check. Reports spend the `communityReport` bucket (20 a day) through `consumeRateLimit`. The public list and "my routes" are keyset-paged (`?cursor=` / `nextCursor`). A route an admin removed (or its owner deleted while an admin had it hidden) sets `blocks_resubmit`, refusing the same track again. Community ids are not in `ALLOWED_TRAILS`: no comments, descriptions or plan sync for them yet.

### Comments API Worker: comment targets and limits (`workers/comments-api/`)

A comment's `waypointId` is checked by its prefix (`validateCommentTarget` in `src/validation.ts`): `w_` + 8-40 hex (the curated registry, form only — the worker carries neither the registry nor the POI lists), `hw_` + a lowercase v4 uuid (must be a shared waypoint the server holds on that trail: 404 `waypoint_not_found` if not, 410 `waypoint_deleted` once tombstoned), or `osm_<node|way|relation>_<safe integer>` (`poiCommentId`). Anything else is 400 `invalid_waypoint`, since no screen would show it. `test/comment-guards.test.ts` holds every id in `data/waypoint-ids.json` to it. The phone's drain holds a comment on the hiker's own `hw_` waypoint while that waypoint's share is still pending or in flight (`outboxRepo.hasPending`; gated like a photo on its comment, re-checked pass after pass until a pass sends nothing). A share that failed is not waited on: the comment goes and takes the 404. A replay of a stored comment is answered before the body is validated, and a request that loses the insert race to its own replay hands its rate-limit unit back (`refundRateLimit`). Plans and curated descriptions still take the looser `^[a-z0-9_-]{4,64}$`. Every rate limit, the comment post (60 a day) and comment report (20 a day) limits included, goes through `consumeRateLimit` in `src/rate-limit.ts`; never count a table's rows and insert after, which a parallel burst gets past.

### Comments API Worker: shared hiker waypoints (`workers/comments-api/`)

`src/shared-waypoints.ts` (migration `0007`): D1 `shared_waypoints` + `shared_waypoint_reports`. `PUT /v1/waypoints/:id` creates (the client-minted `hw_` id is the idempotency key) or is the owner's edit — an identical PUT is a replay that leaves `updated_at` alone; one its owner deleted (made private) is revived by the owner's next PUT, under the same id; one an admin or reports hid answers 410; every write stamps `updated_at` just before the statement that commits it, so a concurrent delta read cannot get ahead of it; `sharedWaypointCreate` (20 a day) and `sharedWaypointEdit` (60) rate buckets. `DELETE` is owner or admin. `POST /v1/waypoints/:id/report` is one per reporter (`sharedWaypointReport`, 20 a day; not your own), and `USER_WAYPOINT_LIMITS.reportsToHide` (3) distinct reporters tombstone it (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`) and only reports filed after the last admin restore (`restored_at`). `POST /v1/admin/waypoints/:id/restore` undoes an admin or report hide (not an owner's delete). `GET /v1/trails/:trailId/waypoints?since=` is the public full/delta read (tombstones in delta mode, 2,000 rows a page, keyset-paged by `(updated_at, id)` through `nextCursor` like the comments feed); a token, when sent, adds `mine`. `GET /v1/admin/waypoints` lists them reported first. Trails must be in `ALLOWED_TRAILS`, so imports and community routes keep their waypoints private. Deleting an account tombstones its shared waypoints, as it does its comments.

**Deploying the comments API:** a merged change to `workers/comments-api/` is not live until someone runs `npm run migrate:remote && npm run deploy` there, from `main`. Shipped app builds call it, so deploy after the merge rather than at the next release, and run the route probes in `docs/mobile-test-build.md` ("Full release", step 1); `/health` answers while a new route 404s (#141).

### Comments API Worker: comment moderation (`workers/comments-api/`)

`src/reports.ts`, `src/comments.ts`, `src/moderation.ts` (migration `0008`, which rebuilds `comments` and `comment_reports` because SQLite cannot widen a CHECK — dropping a referenced table fails D1's foreign-key check even deferred, so the pair is rebuilt together). Comments are moderated like shared waypoints: `COMMENT_REPORTS_TO_HIDE` (3) distinct reporters tombstone one (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`), never the author, and only reports filed after the last admin restore (`restored_at`). A report hide keeps the photos; `POST /v1/admin/comments/:id/restore` undoes it, and an owner's or admin's `DELETE` (or account deletion) makes it final and purges them (from R2 and from `photo_urls_json`) — an owner or admin delete cannot be restored. `GET /v1/admin/comments?reported=1` and `GET /v1/admin/waypoints` carry every report (reason, detail, reporter) and whether the author is banned. `POST /v1/admin/users/:id/ban` `{ banned, removeContent? }` bans or unbans (never an admin); `removeContent` admin-deletes the account's comments and shared waypoints. A ban sets `users.banned_at`; account deletion sets `is_banned` and `users.deleted_at`, and a deleted account can never be unbanned (the migration backfills both columns: deleted accounts by their fixed display name and revoked tokens, every other banned account as banned). The admin listings carry `userBanned`, `userAdmin` and `userDeleted`, so the page offers only the ban actions the server will take. Every tombstone the ban writes is stamped after its reads, just before the batch that commits it. The admin page is `src/web/admin-moderation.html` (unlinked, noindex, client `src/web/api/moderation.ts`).

## Key Patterns

- **Build-time processing**: Trail data is processed at build time into optimized JSON
- **Static site**: All pages are pre-generated, no runtime server required
- **Client-side rendering**: Trail viewer loads JSON data and renders interactively
- **Web maps**: Leaflet with OpenTopoMap tiles for topographic display
- **The app informs the hiker's decisions; it never makes them.** Pace, hours per day, and any other figure that says how far or how long is "reasonable" is the hiker's input, not ours. A UI module must never fix such a figure in a constant (the web plan page's former `RESUPPLY_BASE_KMH = 4` / `DEFAULT_RESUPPLY_DAILY_HOURS = 8` are the named example, removed per `plans/resupply-mobile.md` Phase 0): give the page the input the phone already has, persist it with the plan, and feed the calculator from it. A *default* is fine only as the initial value of an input the hiker can see and change; a shared calculator should require the figure rather than silently substitute one. The same applies to thresholds that colour a judgement — "long carry", "dry stretch", grams of food per day — which are inputs too (`PlanThresholds` in `plan-types.ts`, issue #153): the calculators require them, and like pace and hours they are kept per device (web `PlanUiPrefs`, mobile `plan-inputs-store`), not in the synced `PlanDocument`, because they describe the hiker and a shared plan is read against the reader's own

### Key Expo Concepts

- **Continuous Native Generation (CNG)**: `ios/` and `android/` are generated from `app.json` + config plugins via `npx expo prebuild`. They are build artifacts, not source files. Regenerate with `--clean` after config changes.
- **Config plugins**: Declared in `app.json` `"plugins"` array. They modify native project files during prebuild (e.g. MapLibre adds location permissions automatically).
- **Development builds**: Custom debug apps built via EAS that include your native dependencies. Rebuild only when native deps change; JS changes hot-reload.
- **EAS Build profiles** (`eas.json`): `base` (shared env), `development` (dev client), `development-device` (dev client on a physical device), `preview` (internal testers — a standalone `.apk` you can sideload; how to build and install one is `docs/mobile-test-build.md`), `production` (app store — an `.aab`).
- **EAS Update**: OTA JavaScript updates. Not available in this app yet — `expo-updates` is not installed and `app.json` has no `updates`/`runtimeVersion` — so every change, JS included, ships as a new build.
- **Expo Router**: File-based routing where files in `app/` become navigation routes. `_layout.tsx` defines navigators, `(groups)/` organize without adding URL segments, `[param].tsx` for dynamic routes.

### Verification After Dependency Changes

1. `npx expo prebuild` — ensures config plugins resolve and native projects generate correctly
2. `eas build --profile development --platform android` — ensures the development build compiles with the updated dependencies

### Mobile App Architecture

The app is named **Tracknotes** (`app.json` name/slug `tracknotes`, package `com.tracknotes.app`, URL scheme `tracknotes://`). The app icon, Android adaptive layers, splash image and the website's favicons (`public/favicon.svg`, `favicon-32.png`, `apple-touch-icon.png`, linked from every page's `<head>`) are one piece of artwork generated by `mobile/scripts/build-app-icons.mjs` (`npx -y -p @resvg/resvg-js node scripts/build-app-icons.mjs` from `mobile/`); change the mark there, not in the PNGs. The mark is a dashed footpath passing below a summit spot over real contours: Mt Sonder on the Larapinta Trail, traced from Copernicus GLO-30 by the root `npm run trace:mark-contours` (`scripts/trace-mark-contours.ts`, over `scripts/lib/dem-sampler.ts`; `NODE_USE_ENV_PROXY=1` behind a proxy) into the committed `mobile/scripts/data/mark-contours.json`, so building the icons never touches the network. Smaller sizes drop contour levels and thicken strokes rather than redraw, and the 32 px favicon draws the path solid. Keep the path off the summit spot (a line ending on a dot reads as a pin) and the splash a disc (Android 12+ shows the splash icon in a circle).

- **Map**: MapLibre React Native. Style objects are resolved before mount via `src/services/online-style-service.ts` (online) or `tileManager.getOfflineStyle()` (offline); the bundled base style is `mobile/assets/topo-style.json`, synced from `scripts/topo-style.json` with root `npm run sync:style`. Contours come from `EXPO_PUBLIC_CONTOUR_TILE_URL`, from the worker's `contours` (Australia) source for a trail inside that archive's bounds and its `world` source for every other trail (`contourSourceFor` in `online-style-service.ts`) — the Australia archive returns empty tiles abroad.
- **Map theme**: the map follows the app theme (`useTheme().isDark`), not a setting of its own. Dark is a *night topo*, not a separate style: `src/services/night-style.ts` repaints every layer of the light style — Liberty online, `topo-style.json` offline — by colour role (areas inverted into a dark band, lines compressed so roads stay lighter than the ground, text lifted, halos darkened, hue kept), so forest, parks, water, paths and relief survive in dark mode. (It replaced OpenFreeMap's Dark-Matter `dark` style, which drew a near-black map with none of them.) Offline, the paint patch `scripts/topo-style-dark.json` (also synced by `npm run sync:style`) is merged over the repaint for the layers it does not suit — today only the contours, whose ink matches the online contour layers; a test asserts every id in it still exists in the template. Overlay cartography (tracks, marker/label ink, the fallback style) is per-theme in `features/map/map-style.ts` — `trackColors(theme)` / `mapInk(theme)` — and the theme is part of `mapRemountKey`, because swapping a live map's style object can kill the native renderer.
- **Storage**: trail content is read via `src/services/trail-loader.ts` — there is no `trails` SQLite table. Sources: bundled JSON assets (the seed), newer copies downloaded from R2, catalog-only trails, community routes, and user imports. SQLite (`expo-sqlite`) holds per-guide state, comments + outbox, favorites, and custom routes. Tile files live in `expo-file-system`.
- **Over-the-air trail data** (runbook: `docs/trail-data-updates.md`): `services/trail-data-updates.ts` fetches `{EXPO_PUBLIC_TILE_BASE_URL}/trails/v1/catalog.json` on launch/foreground (`hooks/useTrailDataUpdates`, throttled to 6 h; My Guides pull-to-refresh forces it) and downloads newer content-addressed trail files to `{documentDir}/trail-data/` (size + md5 + shape checked on a `.part` file before `state.json` names it; `state.json` itself is written to a temp file and renamed into place). The pure rules are `services/trail-catalog.ts`: a copy replaces another only when its `updatedAt` is strictly later, so a newer APK beats an older download and unpublished build data is never reverted. A downloaded copy of a bundled trail makes the sync `getTrailJson` return null (callers fall back to async `loadTrail`); use `getBundledTrailJson` only where stale data is fine. Catalog-only trails (`source: 'remote'`) are listed from the last catalog, downloaded on first open by `GuideProvider` (or the shared-plan screen), and registered with `isServerKnown` via `registerRemoteTrailIds`. An open guide keeps the data it opened with until the hiker taps Reload on the banner it shows once a newer copy is installed (`GuideContext` `dataUpdate`, compared by `trailDataVersion`, the md5; `GuideUpdateBanner`); Settings → Guide updates forces a check
- **Hiker waypoints** (`@lib/user-waypoints`): SQLite `user_waypoints` (schema v7, `db/user-waypoints-repo.ts`) holds both kinds; `state/user-waypoints-store.ts` mirrors a trail's rows and re-reads on every `SyncChange` with `userWaypoints: true`. `GuideProvider` places them into the trail (`placeUserWaypoints`) before direction is applied, so `trail` and `baseTrail` carry them and the map, list, profile, detail screen and planner need no special case. Writes go through `sync/waypoint-sync.ts` (`saveUserWaypoint`, `deleteUserWaypoint`, `reportUserWaypoint`): SQLite first, then for a shared one an outbox row (`waypoint` — a full replace, newest only — `waypoint-delete`, `waypoint-report`) that `comment-sync`'s drain sends; a shared → private edit deletes the server copy. A 410 on the `waypoint` PUT, or a tombstone pulled for one of this account's own, keeps the hiker's copy as a private waypoint (`keepAsPrivate`) rather than deleting the only record of the place. `pullTrail` pulls shared waypoints as a third channel (`sync_state.waypoints_synced_at`, every page), skipping any with a write still queued (one outbox read, the rows applied in one transaction). The waypoint detail screen says who added one, offers Edit (own) or Report (another hiker's shared one), and has no comments on a private one. `deleteTrailScopedRows` clears them with the guide
- **Community routes** (`c_…`, `TrailSource 'community'`): `services/community-routes.ts` caches `GET /v1/community/routes` in `{documentDir}/community/state.json`, refreshed alongside trail data (30-minute throttle, forced by pull-to-refresh), and downloads a route's `trailUrl` on first open with size, md5 and shape checks, and again when the list's md5 changes (owner edit, de-attribution). A list never deletes anything: it can be truncated, stale or briefly empty, so each downloaded route it leaves out is probed (`GET /v1/community/routes/:id`, no token, `no-store`, ≤ 20 per refresh) and only a 404 marks it `takenDown` — kept on the phone, shown as "No longer shared" in My Guides and the guide banner, cleared if a list names it again. Opening a route that 404s shows "This route is no longer shared" (no retry) and forces a list refresh. Long-press on a community card: About & report, Remove from this phone. Removing a route or the owner deleting it runs `services/local-trail-data.deleteLocalTrailData` (custom routes, favourites, waypoint_meta, comments/outbox/sync_state, plan, `plan-inputs-store`, direction, current-hike pin), the same cleanup an imported trail's delete runs. Pure rules in `community-catalog.ts` (`planCommunitySync`, `classifyCommunityProbe`); the client is `api/community.ts`. `isServerKnown` refuses `c_` as it refuses `u_` (`isLocalOnlyTrailId`), so a community route gets no comments, plan sync or descriptions, and borrows offline packs like an import. A hidden route is never in the list or My Guides; its owner finds it under Settings → My shared routes (`features/community/useMySharedRoutes.ts`).
- **Shared code**: `src/lib/` (repo root) modules imported via `@lib`. Currently used: elevation-axis, format-distance, region-detect, map-glyphs, waypoint-glyphs, position-on-trail, community-types, community-checks, trail-regions, comments-api-types, track-geometry, plan-types, plan-alternates, day-calculator, day-suggest, resupply-calculator, water-carry-calculator, distance, types, trail-reverse, trail-types, route-breaks, gpx-import, xml-adapter-fxp, poi-display, contribution-licence. Every `src/lib` module is RN-safe: `gpx-parser`/`gpx-optimizer` no longer reach for `DOMParser` (mobile passes `fxpXmlAdapter`), and `gpx-import` avoids `crypto` entirely. jsdom stays out of `src/lib` — its adapter lives in `scripts/lib/xml-adapter-jsdom.ts`.
- **Navigation**: a single Expo Router Stack — "My Guides" list → per-trail guide (nested stack). No bottom tabs. Inside a guide, a segmented control switches three always-mounted panes: Map | Elevation | List (`src/features/guide/GuideView.tsx`).
- **State**: Zustand stores in `src/state/` (settings, downloads, favorites, identity, plans) plus per-guide React contexts. Per-trail pace and daily hours are in `features/plan/plan-inputs-store.ts`; the resupply selection is in the plan document (`state/plans-store.ts`), and `use-planned-resupply.ts` is the one source of "planned resupply" for the map, profile, list, detail screen and distance strip — `null` until a plan is made, and `null` means nothing is planned, never everything.
- **OSM points of interest**: bundled trails carry `pois` (slimmed by `build-mobile-trails.ts`), imported ones whatever the `.tracknotes.json` handoff brought (a GPX imported on the phone has none — the on-phone Overpass search is a follow-up, see `plans/pois-mobile.md`). POIs are never waypoints: they are not in the plan calculators, the GPS distance strip or favorites, and `duplicateOf` entries are never drawn or listed (their OSM detail shows on the waypoint they duplicate instead). One global `poiFilter` in the settings store (master switch + six categories) drives every surface through `features/guide/use-visible-pois.ts`; the map's layers sheet edits it, and so do the planner's chips (`features/plan/PoiFilterChips.tsx`, on the Today screen and above the Plan screen's day splits) — the planner never keeps a filter of its own. Map markers are smaller, thin-ringed badges hidden below zoom 11; the List pane interleaves POI rows (an "OSM" pill) by km; the elevation profile draws hollow ticks only when zoomed to ≤ 60 km; the Today screen lists the day's visible POIs among its waypoints as OSM rows (km from the start, off-trail distance, opening hours) that never split a waypoint's leg (`today-plan` `todayPois`/`todayEntries`), and each Plan day card counts them ("Along the way (OSM)", `DaySplitList` `dayPoiSummary`) — still never in the calculators' figures; `guide/[trailId]/poi/[poiKey]` is the detail screen. A POI takes comments like a waypoint, filed under `poiCommentId` (the worker needs no change: the id is just another waypoint id on an allowed trail). Direction reversal mirrors POI km inside `@lib/trail-reverse`, so nothing on mobile special-cases it.

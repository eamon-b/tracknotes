## Comments API Worker: community routes (`workers/comments-api/`)

`src/community.ts` / `src/community-review.ts` (migrations `0005`, `0006`): D1 `community_routes` + `community_route_reports`. A submit re-runs `@lib/community-checks` (with the uploaded GPX as `gpxText`, for the `speed` check) and stores *its* rebuilt trail, never the client's JSON, with `config` rewritten server-side (id, name, `source: 'community'`, country/states, description, CC0 `dataSource`). The bucket has no private area (all of it is served at `PHOTOS_PUBLIC_BASE`), so private objects live at unguessable keys recorded in the row and never returned: the canonical trail JSON at `community/private/<id>/<32 random hex>.json` (`private_key`) and the optional raw GPX (≤ 5 MB) beside it as `.gpx` (`gpx_key`; a file whose head is not `<gpx` is dropped, not refused). While a route is live, a public copy of the same bytes sits at `community/v1/<id>.<md5[0..12]>.json` (`r2_key`; `max-age=300`, so an edge copy outlives a hide by minutes, not a year). An owner's edit writes new objects, keeps the public version it replaced (cached lists still name it) and purges older ones; a de-attribution purges the old public versions at once, since they name the deleted account; hiding a route (AI review, reports or admin) deletes every object under `community/v1/<id>.` and NULLs `r2_key`, so owner/admin detail of a hidden route has `trailUrl: null`; an admin restore from hidden always republishes from the private copy (if it is gone: 404 when removed meanwhile, 409 `conflict` when the row changed, else 500 `trail_missing`), and a hide re-reads the row after its purge and republishes a route a restore made live meanwhile; removal purges both prefixes. Every row change sets `updated_at` strictly later than the value it read (`stampAfter`); an owner's PATCH, an admin status change, a de-attribution and the AI review write only if `status`/`updated_at` still match the row they read — a lost race returns 409 `conflict` (PATCH, admin) or retries (de-attribution) and deletes the objects it wrote, and a stale review writes nothing (its verdict write leaves `updated_at` alone). `@lib/community-checks` rebuilds every distance and climb from the coordinates (point km, length, display points, waypoint and variant km, 3 m-hysteresis climb) and drops client route breaks, POIs and `cumAscent`/`cumDescent`, so no client-claimed distance or climb is stored. The duplicate hash is sha256 of the trail without its `config`, so a rename does not get past it (the 409 carries `existingId` only for the caller's own route; the near-duplicate warning names the other route by id); a body whose non-GPX part exceeds 4 MB + 64 KB is refused 413 `trail_too_large` before it is checked; the 10-a-day `communitySubmit` limit is spent only after the checks pass and the stored JSON measures ≤ 4 MB, `communitySubmitAttempt` (30 a day) is spent by every submit before its body is parsed, and `communityEdit` (20 a day) by every PATCH that changes something. The `claude-sonnet-5-5` review (structured output, `fallbacks: 'default'`, all route text fenced as untrusted) runs from `waitUntil` (SDK client with a 20 s timeout and 1 retry) and **fails open** — `skipped` without the `ANTHROPIC_API_KEY` secret (`wrangler secret put ANTHROPIC_API_KEY`), `failed` on an API error or refusal. The review also sees a bounded sample of waypoint descriptions, the variant names, and a sample of off-trail and variant waypoint names (≤ 200 names in all, at least 50 of them off-trail/variant when there are that many). A reject with confidence ≥ 0.8, or 3 distinct reports filed after the route's last admin status change (`status_changed_at`) by accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`; younger accounts' reports are stored but do not count), hides an *unverified* route; a verified one stays up and rises to the top of the admin queue. An owner's detail of a hidden route (`GET /v1/me/community/routes`, or `GET /v1/community/routes/:id` with their token) carries `hiddenReason` (`'review' | 'reports' | 'admin'`). It is derived from the hide's `status_note`: the review and report hides write the fixed `REVIEW_HIDE_NOTE`/`REPORTS_HIDE_NOTE`, and anything else counts as an admin hide. `statusNote` itself stays admin-only, and an admin note equal to either fixed note is refused 400 `invalid_note`. Only an admin verifies. Deleting an account de-attributes its routes (CC0) rather than removing them; `deattribute_pending` keeps that durable, and a Cron Trigger (`*/15 * * * *`, `runCommunityMaintenance` in `src/index.ts`'s `scheduled`) retries pending de-attributions and re-runs AI reviews left `pending` over 10 minutes. A submit also adds the `region` check (`checkCommunityRegion`: a warning when the coordinates are in another country or state, never a change to the hiker's choice), and a PATCH that changes the region re-runs it. A PATCH re-runs the `metadata` check. Reports spend the `communityReport` bucket (20 a day) through `consumeRateLimit`. The public list and "my routes" are keyset-paged (`?cursor=` / `nextCursor`). A route an admin removed (or its owner deleted while an admin had it hidden) sets `blocks_resubmit`, refusing the same track again. Community ids are not in `ALLOWED_TRAILS`: no comments, descriptions or plan sync for them yet.

## Comments API Worker: comment targets and limits (`workers/comments-api/`)

A comment's `waypointId` is checked by its prefix (`validateCommentTarget` in `src/validation.ts`): `w_` + 8-40 hex (the curated registry, form only — the worker carries neither the registry nor the POI lists), `hw_` + a lowercase v4 uuid (must be a shared waypoint the server holds on that trail: 404 `waypoint_not_found` if not, 410 `waypoint_deleted` once tombstoned), or `osm_<node|way|relation>_<safe integer>` (`poiCommentId`). Anything else is 400 `invalid_waypoint`, since no screen would show it. `test/comment-guards.test.ts` holds every id in `data/waypoint-ids.json` to it. The phone's drain holds a comment on the hiker's own `hw_` waypoint while that waypoint's share is still pending or in flight (`outboxRepo.hasPending`; gated like a photo on its comment, re-checked pass after pass until a pass sends nothing). A share that failed is not waited on: the comment goes and takes the 404. A replay of a stored comment is answered before the body is validated, and a request that loses the insert race to its own replay hands its rate-limit unit back (`refundRateLimit`). Plans and curated descriptions still take the looser `^[a-z0-9_-]{4,64}$`. Every rate limit, the comment post (60 a day) and comment report (20 a day) limits included, goes through `consumeRateLimit` in `src/rate-limit.ts`; never count a table's rows and insert after, which a parallel burst gets past.

## Comments API Worker: shared hiker waypoints (`workers/comments-api/`)

`src/shared-waypoints.ts` (migration `0007`): D1 `shared_waypoints` + `shared_waypoint_reports`. `PUT /v1/waypoints/:id` creates (the client-minted `hw_` id is the idempotency key) or is the owner's edit — an identical PUT is a replay that leaves `updated_at` alone; one its owner deleted (made private) is revived by the owner's next PUT, under the same id; one an admin or reports hid answers 410; every write stamps `updated_at` just before the statement that commits it, so a concurrent delta read cannot get ahead of it; `sharedWaypointCreate` (20 a day) and `sharedWaypointEdit` (60) rate buckets. `DELETE` is owner or admin. `POST /v1/waypoints/:id/report` is one per reporter (`sharedWaypointReport`, 20 a day; not your own), and `USER_WAYPOINT_LIMITS.reportsToHide` (3) distinct reporters tombstone it (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`) and only reports filed after the last admin restore (`restored_at`). `POST /v1/admin/waypoints/:id/restore` undoes an admin or report hide (not an owner's delete). `GET /v1/trails/:trailId/waypoints?since=` is the public full/delta read (tombstones in delta mode, 2,000 rows a page, keyset-paged by `(updated_at, id)` through `nextCursor` like the comments feed); a token, when sent, adds `mine`. `GET /v1/admin/waypoints` lists them reported first. Trails must be in `ALLOWED_TRAILS`, so imports and community routes keep their waypoints private. Deleting an account tombstones its shared waypoints, as it does its comments.

## Comments API Worker: comment moderation (`workers/comments-api/`)

`src/reports.ts`, `src/comments.ts`, `src/moderation.ts` (migration `0008`, which rebuilds `comments` and `comment_reports` because SQLite cannot widen a CHECK — dropping a referenced table fails D1's foreign-key check even deferred, so the pair is rebuilt together). Comments are moderated like shared waypoints: `COMMENT_REPORTS_TO_HIDE` (3) distinct reporters tombstone one (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`), never the author, and only reports filed after the last admin restore (`restored_at`). A report hide keeps the photos; `POST /v1/admin/comments/:id/restore` undoes it (the restore reaches the author's phone through the public `GET /v1/trails/:trailId/comments?since=` feed, which, like the waypoints feed, adds `mine` to live rows when a token is sent — a bad or expired token reads as anonymous, and a token-bearing response is `Cache-Control: private, no-store`), and an owner's or admin's `DELETE` (or account deletion) makes it final and purges them (from R2 and from `photo_urls_json`) — an owner or admin delete cannot be restored. `GET /v1/admin/comments?reported=1` and `GET /v1/admin/waypoints` carry every report (reason, detail, reporter) and whether the author is banned. `POST /v1/admin/users/:id/ban` `{ banned, removeContent? }` bans or unbans (never an admin); `removeContent` admin-deletes the account's comments and shared waypoints. A ban sets `users.banned_at`; account deletion sets `is_banned` and `users.deleted_at`, and a deleted account can never be unbanned (the migration backfills both columns: deleted accounts by their fixed display name and revoked tokens, every other banned account as banned). The admin listings carry `userBanned`, `userAdmin` and `userDeleted`, so the page offers only the ban actions the server will take. Every tombstone the ban writes is stamped after its reads, just before the batch that commits it. The admin page is `src/web/admin-moderation.html` (unlinked, noindex, client `src/web/api/moderation.ts`).

## Contour Tile Worker (`workers/contour-tiles/`)

Cloudflare Worker serving contour vector tiles from PMTiles on R2. URL pattern: `/{source}/{z}/{x}/{y}.pbf`. Uses R2 bucket `aus-map-data` with PMTiles at `contours/australia.pmtiles` (source `contours`) and `contours/world.pmtiles` (source `world`, used for trails outside Australia). Built with `wrangler`.

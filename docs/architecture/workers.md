# Cloudflare workers (`workers/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

## Comments API Worker: community routes (`workers/comments-api/`)

`src/community.ts` / `src/community-review.ts` (migrations `0005`, `0006`; `0009` for POIs): D1 `community_routes` + `community_route_reports`. A submit re-runs `@lib/community-checks` (with the uploaded GPX as `gpxText`, for the `speed` check) and stores *its* rebuilt trail, never the client's JSON, with `config` rewritten server-side (id, name, `source: 'community'`, country/states, description, CC0 `dataSource`). The bucket has no private area (all of it is served at `PHOTOS_PUBLIC_BASE`), so private objects live at unguessable keys recorded in the row and never returned: the canonical trail JSON at `community/private/<id>/<32 random hex>.json` (`private_key`) and the optional raw GPX (≤ 5 MB) beside it as `.gpx` (`gpx_key`; a file whose head is not `<gpx` is dropped, not refused). While a route is live, a public copy of the same bytes sits at `community/v1/<id>.<md5[0..12]>.json` (`r2_key`; `max-age=300`, so an edge copy outlives a hide by minutes, not a year). An owner's edit writes new objects, keeps the public version it replaced (cached lists still name it) and purges older ones; a de-attribution purges the old public versions at once, since they name the deleted account; hiding a route (AI review, reports or admin) deletes every object under `community/v1/<id>.` and NULLs `r2_key`, so owner/admin detail of a hidden route has `trailUrl: null`; an admin restore from hidden always republishes from the private copy (if it is gone: 404 when removed meanwhile, 409 `conflict` when the row changed, else 500 `trail_missing`), and a hide re-reads the row after its purge and republishes a route a restore made live meanwhile; removal purges both prefixes. Every row change sets `updated_at` strictly later than the value it read (`stampAfter`); an owner's PATCH, an admin status change, a de-attribution, the AI review and the POI enrichment write only if `status`/`updated_at` still match the row they read — a lost race returns 409 `conflict` (PATCH, admin) or retries (de-attribution) and deletes the objects it wrote, and a stale review writes nothing (its verdict write leaves `updated_at` alone). `@lib/community-checks` rebuilds every distance and climb from the coordinates (point km, length, display points, waypoint and variant km, 3 m-hysteresis climb) and drops client route breaks, POIs and `cumAscent`/`cumDescent`, so no client-claimed distance or climb is stored. The duplicate hash is sha256 of the trail without its `config`, so a rename does not get past it (the 409 carries `existingId` only for the caller's own route; the near-duplicate warning names the other route by id); a body whose non-GPX part exceeds 4 MB + 64 KB is refused 413 `trail_too_large` before it is checked; the 10-a-day `communitySubmit` limit is spent only after the checks pass and the stored JSON measures ≤ 4 MB, `communitySubmitAttempt` (30 a day) is spent by every submit before its body is parsed, and `communityEdit` (20 a day) by every PATCH that changes something. The `claude-sonnet-5-5` review (structured output, `fallbacks: 'default'`, all route text fenced as untrusted) runs from `waitUntil` (SDK client with a 20 s timeout and 1 retry) and **fails open** — `skipped` without the `ANTHROPIC_API_KEY` secret (`wrangler secret put ANTHROPIC_API_KEY`), `failed` on an API error or refusal. The review also sees a bounded sample of waypoint descriptions, the variant names, and a sample of off-trail and variant waypoint names (≤ 200 names in all, at least 50 of them off-trail/variant when there are that many). A reject with confidence ≥ 0.8, or 3 distinct reports filed after the route's last admin status change (`status_changed_at`) by accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`; younger accounts' reports are stored but do not count), hides an *unverified* route; a verified one stays up and rises to the top of the admin queue. An owner's detail of a hidden route (`GET /v1/me/community/routes`, or `GET /v1/community/routes/:id` with their token) carries `hiddenReason` (`'review' | 'reports' | 'admin'`). It is derived from the hide's `status_note`: the review and report hides write the fixed `REVIEW_HIDE_NOTE`/`REPORTS_HIDE_NOTE`, and anything else counts as an admin hide. `statusNote` itself stays admin-only, and an admin note equal to either fixed note is refused 400 `invalid_note`. Only an admin verifies. Deleting an account de-attributes its routes (CC0) rather than removing them; `deattribute_pending` keeps that durable, and a Cron Trigger (`*/15 * * * *`, `runCommunityMaintenance` in `src/index.ts`'s `scheduled`) retries pending de-attributions, re-runs AI reviews left `pending` over 10 minutes, and adds OSM POIs to routes that have none (see "community route POIs" below). A submit also adds the `region` check (`checkCommunityRegion`: a warning when the coordinates are in another country or state, never a change to the hiker's choice), and a PATCH that changes the region re-runs it. A PATCH re-runs the `metadata` check. Reports spend the `communityReport` bucket (20 a day) through `consumeRateLimit`. The public list and "my routes" are keyset-paged (`?cursor=` / `nextCursor`). A route an admin removed (or its owner deleted while an admin had it hidden) sets `blocks_resubmit`, refusing the same track again. Comments, plan sync and shared hiker waypoints take a community route's id as well as `ALLOWED_TRAILS` (next section).

## Comments API Worker: which trails (`workers/comments-api/src/trails.ts`)

`resolveTrail(env, trailId, use)` is the one trail gate for comments, plans, shared waypoints and the descriptions read. A trail is either curated (`ALLOWED_TRAILS`, held equal to the bundled trails by `scripts/server-trail-allowlist.test.ts`) or a community route (`isCommunityRouteId`, plus a row in `community_routes`: one primary-key read). Anything else — a `u_` import above all — is 400 (`invalid_trail`; `trail_not_allowed` for a plan). What a route takes depends on its status: a **public write** (`PUT /v1/comments/:id`, `PUT /v1/waypoints/:id`, a new share or an edit) needs a live route (`unverified`/`verified`), else 403 `trail_not_live`, so nothing new is published on a route nobody can see; a **private write** (`PUT /v1/plans/:id`) and the **reads** (`GET /v1/trails/:id/waypoints`, `/descriptions`) take any route the server has a row for, hidden or removed included — a plan is the hiker's own, and the phone keeps a route that was taken down ("No longer shared"); the feeds keep serving what was posted while it was up (the comment feeds never checked the trail). Deletes, reports and replays are not gated by trail. Rows are never deleted (removal is a tombstone), so "is a community route" is cached for the isolate's life and "is live" for `LIVE_CACHE_MS` (60 s, live results only): a hide stops new comments within a minute on every isolate, and a restore is read at once. The descriptions read answers an empty list for a route (its descriptions are in the route itself); the admin description PUT stays curated-only (`validateTrailId`).

## Comments API Worker: community route POIs (`workers/comments-api/`)

`enrichCommunityRoutePois` in `src/community.ts` (the third task of the `*/15` cron's `runCommunityMaintenance`, after the de-attribution retry and the stale-review re-run, so it never races a review on the same row) and `src/community-pois.ts` (migration `0009`). A submit stores the route without POIs (`runCommunityChecks` drops any the client sent; that stays so — POIs come only from the server) and never waits on Overpass. A later run asks Overpass for the POIs within 2 km of the route — main track, alternates and side trips — exactly as `scripts/fetch-pois.ts` does: `@lib/trail-poi-search` `planTrailPoiSearch` cuts it into the build's corridor queries (`@lib/osm-poi`/`@lib/poi-enrichment`, the `gpx-tools` port the phone runs too), and its `finishTrailPois` places the answers on the trail's km and runs the build's passes (noise, duplicates of the route's own waypoints, city thinning; no `TrailPoiConfig`, which a community route never has) and `slimPoi`, and republishes the trail JSON with a `pois` array: a new private and public object, `md5`/`bytes`/`updated_at` moved (so phones see the md5 change and download it again), guarded on `status`/`updated_at` like an owner's edit (a lost race drops its objects), the old private object deleted and older public versions purged as after an edit. A route whose stored POIs come out unchanged is marked done without a rewrite. Because the POIs live in the canonical private JSON, every republish keeps them: an owner's edit and a de-attribution re-store from it, a restore republishes it. `content_hash` is never recomputed, so the duplicate check is unaffected.

Bookkeeping (never returned): `pois_status` (`pending` / `done` / `failed` / `skipped`), `pois_hash` (the `content_hash` the answer was for — a route whose `content_hash` moves on is enriched again at once, so a future geometry edit only has to change the hash; it should also drop the old `pois`), `poi_count`, `pois_attempts`/`pois_attempted_at` (the claim, written before any request so a run the platform stops still counts) and `pois_error`. Candidates are live routes (`unverified`/`verified`) without an answer for their geometry, untouched for 2 minutes (a submit's own review is long done) and not tried in the last hour, least-tried then newest first, 3 a run.

Budget (Workers Free: ~10 ms CPU, 50 external subrequests an invocation; waiting on a fetch is wall time, not CPU): at most 20 Overpass requests a run across every route and endpoint (`POI_RUN_LIMITS`), none started after 6 minutes, 25 s Overpass `[timeout:]` with the request abandoned 5 s later, 1 s between requests. A route needing more than 16 corridor queries (`POI_LIMITS.maxQueriesPerRoute`, roughly 2,500-5,000 km) is `skipped`, never fetched in part; so is one whose answer exceeds 8 MB, or that brings more than 12,000 distinct POIs or would ship more than 4,000, or whose JSON would pass 4 MB. CPU goes on parsing answers and placing POIs; `markDuplicatePois` skips a waypoint on latitude alone before tokenising its name, so the passes stay linear in the POIs. **Fails open**: any query that no endpoint answers (HTTP error, timeout, an Overpass `runtime error` remark, the run's budget running out) makes the attempt fail with nothing stored — the route stays as it is, without POIs — and it is retried an hour later, 4 attempts per geometry, then `failed`. `OVERPASS_ENDPOINTS` (`wrangler.toml` `[vars]`, comma-separated https URLs) lists the instances: each query goes to the one that answered last, then the next; empty switches the enrichment off (tests set it empty and inject a fetch). Mirrors come and go (see `fetch-pois.ts` in `build-scripts.md`); change the list there, no code change needed.

## Comments API Worker: comment targets and limits (`workers/comments-api/`)

A comment's `waypointId` is checked by its prefix (`validateCommentTarget` in `src/validation.ts`, over `@lib/comment-targets`), and the kind must fit the trail's: `w_` + 8-40 hex (the curated registry; curated trails only), `uw_` + 1-40 lowercase alphanumerics with an optional `_<n>` (a community route's own waypoints, the ids its import minted and the server stored as submitted; `c_` routes only — form only, like the curated ids: the worker carries neither the registry, a route's stored trail nor the POI lists, so a route whose file holds some other id for a place takes no comments on it, and the phone offers no composer there), `hw_` + a lowercase v4 uuid (must be a shared waypoint the server holds on that trail: 404 `waypoint_not_found` if not, 410 `waypoint_deleted` once tombstoned), or `osm_<node|way|relation>_<safe integer>` (`poiCommentId`). Anything else is 400 `invalid_waypoint`, since no screen would show it. `test/comment-guards.test.ts` holds every id in `data/waypoint-ids.json` to it. The phone's drain holds a comment on the hiker's own `hw_` waypoint while that waypoint's share is still pending or in flight (`outboxRepo.hasPending`; gated like a photo on its comment, re-checked pass after pass until a pass sends nothing). A share that failed is not waited on: the comment goes and takes the 404. A replay of a stored comment is answered before the body is validated, and a request that loses the insert race to its own replay hands its rate-limit unit back (`refundRateLimit`). Plans and curated descriptions still take the looser `^[a-z0-9_-]{4,64}$`. Every rate limit, the comment post (60 a day) and comment report (20 a day) limits included, goes through `consumeRateLimit` in `src/rate-limit.ts`; never count a table's rows and insert after, which a parallel burst gets past.

## Comments API Worker: shared hiker waypoints (`workers/comments-api/`)

`src/shared-waypoints.ts` (migration `0007`): D1 `shared_waypoints` + `shared_waypoint_reports`. `PUT /v1/waypoints/:id` creates (the client-minted `hw_` id is the idempotency key) or is the owner's edit — an identical PUT is a replay that leaves `updated_at` alone; one its owner deleted (made private) is revived by the owner's next PUT, under the same id; one an admin or reports hid answers 410; every write stamps `updated_at` just before the statement that commits it, so a concurrent delta read cannot get ahead of it; `sharedWaypointCreate` (20 a day) and `sharedWaypointEdit` (60) rate buckets. `DELETE` is owner or admin. `POST /v1/waypoints/:id/report` is one per reporter (`sharedWaypointReport`, 20 a day; not your own), and `USER_WAYPOINT_LIMITS.reportsToHide` (3) distinct reporters tombstone it (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`) and only reports filed after the last admin restore (`restored_at`). `POST /v1/admin/waypoints/:id/restore` undoes an admin or report hide (not an owner's delete). `GET /v1/trails/:trailId/waypoints?since=` is the public full/delta read (tombstones in delta mode, 2,000 rows a page, keyset-paged by `(updated_at, id)` through `nextCursor` like the comments feed); a token, when sent, adds `mine`. `GET /v1/admin/waypoints` lists them reported first. The trail must be curated or a live community route (`resolveTrail`; the listing takes a hidden one too), so imports keep their waypoints private. Deleting an account tombstones its shared waypoints, as it does its comments.

## Comments API Worker: comment moderation (`workers/comments-api/`)

`src/reports.ts`, `src/comments.ts`, `src/moderation.ts` (migration `0008`, which rebuilds `comments` and `comment_reports` because SQLite cannot widen a CHECK — dropping a referenced table fails D1's foreign-key check even deferred, so the pair is rebuilt together). Comments are moderated like shared waypoints: `COMMENT_REPORTS_TO_HIDE` (3) distinct reporters tombstone one (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`), never the author, and only reports filed after the last admin restore (`restored_at`). A report hide keeps the photos; `POST /v1/admin/comments/:id/restore` undoes it (the restore reaches the author's phone through the public `GET /v1/trails/:trailId/comments?since=` feed, which, like the waypoints feed, adds `mine` to live rows when a token is sent — a bad or expired token reads as anonymous, and a token-bearing response is `Cache-Control: private, no-store`), and an owner's or admin's `DELETE` (or account deletion) makes it final and purges them (from R2 and from `photo_urls_json`) — an owner or admin delete cannot be restored. `GET /v1/admin/comments?reported=1` and `GET /v1/admin/waypoints` carry every report (reason, detail, reporter) and whether the author is banned. `POST /v1/admin/users/:id/ban` `{ banned, removeContent? }` bans or unbans (never an admin); `removeContent` admin-deletes the account's comments and shared waypoints. A ban sets `users.banned_at`; account deletion sets `is_banned` and `users.deleted_at`, and a deleted account can never be unbanned (the migration backfills both columns: deleted accounts by their fixed display name and revoked tokens, every other banned account as banned). The admin listings carry `userBanned`, `userAdmin` and `userDeleted`, so the page offers only the ban actions the server will take. Every tombstone the ban writes is stamped after its reads, just before the batch that commits it. The admin page is `src/web/admin-moderation.html` (unlinked, noindex, client `src/web/api/moderation.ts`).

## Contour Tile Worker (`workers/contour-tiles/`)

Cloudflare Worker serving contour vector tiles from PMTiles on R2. URL pattern: `/{source}/{z}/{x}/{y}.pbf`. Uses R2 bucket `aus-map-data` with PMTiles at `contours/australia.pmtiles` (source `contours`) and `contours/world.pmtiles` (source `world`, used for trails outside Australia). Built with `wrangler`.

# Web UI (`src/web/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

- `index.html` / `index.ts` - Landing page: filter bar (search, length chips, sort; `localStorage` `trail-maps-list-filter`), Featured (hidden when empty), curated trails grouped Country → State in collapsible sections, Community routes (only when `VITE_API_BASE_URL` is set, Verified/Unverified badges; the list has a 10 s deadline, after which the tier shows its error note), My trails (IndexedDB) with a "Shared by me" block when the API is set and the browser is linked: the reader's own routes from `listMyCommunityRoutes` (same 10 s deadline, fetched in parallel; failures stay inside the block; a 401 clears the session and offers the link form), hidden ones with why (`hiddenReasonText`) and the review summary. Rendering is pure and tested in `index.test.ts`; styles in `trail-list.css`
- `styles.css` - Global styles and the light/dark theme tokens
- `theme.ts` - Light/dark/system theme: applies `data-theme` to `<html>`, renders the toggle, and exposes `onThemeChange()`/`themeColor()` so canvas and Chart.js code can follow the theme
- `trails/trail-template.html` - Template for individual trail pages
- `trails/trail-viewer.ts` - Interactive trail viewer (map, elevation profile, waypoints). The main route is one Leaflet polyline per stretch on the default SVG renderer: Polyline's `smoothFactor` already runs Douglas-Peucker in screen pixels per reprojection, so a 20,000-point line costs the browser no more vertices than the zoom can resolve. Map hover goes through `@lib/point-index` — set `displayPoints` only via `setDisplayPoints`, which rebuilds that index. The waypoints table ("datasheet") filters to the water or food/resupply family via `@lib/waypoint-taxonomy`; when filtered, the leg columns are recomputed between *visible* rows so resupply-leg distances read directly off the table. Row interaction is delegated from `#waypoints-container`, not the tbody, because every re-render replaces the tbody
- `trails/climate-template.html` - Template for climate data pages
- `trails/plan-template.html` - Template for plan visualization pages
- `trails/plan-shell.html` - The one copy of the plan page's `#plan-shell` markup (header + three panels). `build-trails.ts` inlines it into `plan-template.html` and the `plan-shell` Vite plugin inlines it into `my-plan.html` at the `<!-- @plan-shell -->` marker, with per-page header fills from `scripts/lib/plan-shell.ts`
- `trails/plan-viewer.ts` - Interactive plan viewer. The header's pace preset and hours/day inputs are persisted in `PlanState` and feed both `computeDays` and the Resupply tab's legs — the page fixes neither figure. Planned resupply stops are marked on every surface of the page, not only in the Resupply tab: `refreshPlannedResupply()` resolves `@lib/resupply-plan`'s `plannedResupplyIds` once per render, and the day cards, Stops rows, datasheet rows (day boundaries matched on km), map markers and profile ticks all read that one set. `null` — no explicit selection — marks nothing, which is why the every-option default of a fresh plan is not painted as a plan. Alternates: the page holds `storedPlan` (what is saved and synced) and `plan`, its route-km view over `routeTrail` (`@lib/plan-alternates`); `activeTrail()` reverses `routeTrail`, `applyEdit` converts an edit back, and `setAlternate` changes the route. The Stops tab draws the branch/rejoin cards, the map draws the planned route as the base line with every alternate dashed beside it
- `trails/plan-next-days.ts` - The plan page's "Plan the next few days" section, at the top of the Days tab: the web half of the Next days feature (issue 81), over `@lib/plan-suggest` + `@lib/day-suggest`.
  - It starts from the last stop, the trail start, or the browser's location. "Use my location" snaps the fix to the track and shows a "You are here" divider in the Stops tab.
  - It ranks the alternatives. The best is previewed on the map as dashed day lines with numbered flags, and "Use this plan" applies one.
  - It talks to the viewer through `NextDaysHost`, and is removed on a read-only (shared) page.
  - The page also shows the tail after the last stop as a dashed "Not planned yet" card, not a day, via `splitUnplannedTail`.
- `trails/plan-state.ts` - Plan state management: the `PlanDocument` under `trail-plan-doc-<id>`, the one-off migration of the legacy `PlanState` (`trail-plan-<id>`, left in place), and `PlanUiPrefs` under `trail-plan-ui-<id>` — the Stops tab's "show all" switch, the header's pace and hours/day, and the next-days inputs (`suggest`). Pace and hours are per browser, not part of the document (the phone keeps its own in `plan-inputs-store`), and the migration carries a legacy save's values into the prefs. `loadPlanState` rejects a record whose *shape* is wrong, but drops only an unusable `pace`/`dailyHours`
- `upload.html` / `upload.ts` - User GPX import: drag-drop → `importGpx` → report (+ optional elevation backfill) → IndexedDB
- `how-import-works.html` - "How your file is processed" page; the article body is `docs/gpx-import.md`, rendered at build time by the `gpx-import-doc` Vite plugin (GitHub-style heading ids, so `#anchors` against the doc keep working)
- `my-trail.html` / `my-plan.html` (+ `.ts`) - Trail/plan pages for imported trails, booted from `?id=` via `imported-trails-db.ts` and the viewers' `preloadedTrail` argument; "Export for Tracknotes" handoff
- `trails/plan-sync.ts`, `api/` (`client.ts`, `session.ts`, `plans.ts`) - The plan page's sync arm, on only when `VITE_API_BASE_URL` is set (the comments/plans API origin; public, ships in the bundle; unset = local-only planner with the Sync/Share controls removed). A browser links to the phone's identity by entering the code the phone mints (Settings → Linked browsers); the linked token lives in `localStorage` `tracknotes.webSession`, only ever rides in the `Authorization` header, and can be unlinked from the page. Imported (`u_`) trails never sync
- `shared-plan.html` / `shared-plan.ts` - Read-only view of a shared plan (`?s=<shareId>`, public `GET /v1/shared/plans/:id`), with "Open in Tracknotes" (`tracknotes://plan/<shareId>`) and "Copy to my plans". The worker's `SITE_BASE` var builds the share URL and must point at the deployed site
- `api/community.ts` - Typed client for the community-routes API; `listCommunityRoutes` returns null without `VITE_API_BASE_URL`, takes an abort `signal` and drops list entries of the wrong shape (`isCommunityRouteSummary`); `checksFromError` reads a 422's server checks and `duplicateRouteId` a 409's `existingId`. `community-ui.ts` holds the check list, region picker and `localCopyId`; `community-labels.ts` holds the status explanations, the status badge (`statusBadgeHtml`), `hiddenReasonText`, `multilineHtml` and `placeLabel`/`regionLabel` (all re-exported by `community-ui`), kept apart so the landing page does not load `@lib/gpx-import`; `link-browser.ts` is the inline link-code form (over `api/session.ts`) for pages other than the planner. `linkDevice` throws `SessionStorageError` (after revoking the new token) when storage refuses the session, and every page uses the session handed to `onLinked` rather than reading storage back
- `community-share.ts` - The upload page's opt-in "Share with the community" step, loaded lazily after a save when the API is set: live `@lib/community-checks` (given the GPX text as `meta.gpxText` whenever it will be sent), CC0 confirmation, an "Include the original GPX file" box (on by default; the raw GPX goes as base64 only when ticked and ≤ 5 MB), the worker's own message for 409/413/429 (a 409 that names the caller's own route links to it), 401/422 handling. `open()` resets every field for each import. Sharing needs a linked browser (the phone's identity)
- `community-route.html` / `.ts` - Public `?id=c_…` page: detail from the API, trail from `trailUrl`, drawn by the trail viewer as `preloadedTrail`. Report (linked browser; not offered to the owner; kept when only the track download failed), "Save to my trails" (IndexedDB under a `u_` id, so plan sync stays off), "Export for Tracknotes", owner Edit/Delete with checks and the AI review (kept in the no-track view of a hidden route, whose header also says why it was hidden); an owner's edit updates one shared detail that Save, the export and the viewer (`setTrailName`) read
- `admin-community.html` / `.ts` - Unlinked, noindex review queue for admins (AI-rejected/hidden first): Verify / Unverify / Hide / Restore / Re-run review / Delete
- `imported-trails-db.ts` - IndexedDB store (`tracknotes-imports`) for imported `ProcessedTrail`s; `index.html` lists them under "My trails"
- `web-utils.ts` - `escapeHtml`, `getQueryParam` — every user-supplied string (trail names) must go through `escapeHtml`

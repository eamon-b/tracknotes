# Tracknotes mobile app architecture (`mobile/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

## Mobile App Architecture

The app is named **Tracknotes** (`app.json` name/slug `tracknotes`, package `com.tracknotes.app`, URL scheme `tracknotes://`). The app icon, Android adaptive layers, splash image and the website's favicons (`public/favicon.svg`, `favicon-32.png`, `apple-touch-icon.png`, linked from every page's `<head>`) are one piece of artwork generated by `mobile/scripts/build-app-icons.mjs` (`npx -y -p @resvg/resvg-js node scripts/build-app-icons.mjs` from `mobile/`); change the mark there, not in the PNGs. The mark is a dashed footpath passing below a summit spot over real contours: Mt Sonder on the Larapinta Trail, traced from Copernicus GLO-30 by the root `npm run trace:mark-contours` (`scripts/trace-mark-contours.ts`, over `scripts/lib/dem-sampler.ts`; `NODE_USE_ENV_PROXY=1` behind a proxy) into the committed `mobile/scripts/data/mark-contours.json`, so building the icons never touches the network. Smaller sizes drop contour levels and thicken strokes rather than redraw, and the 32 px favicon draws the path solid. Keep the path off the summit spot (a line ending on a dot reads as a pin) and the splash a disc (Android 12+ shows the splash icon in a circle).

- **Map**: MapLibre React Native. Style objects are resolved before mount via `src/services/online-style-service.ts` (online) or `tileManager.getOfflineStyle()` (offline); the bundled base style is `mobile/assets/topo-style.json`, synced from `scripts/topo-style.json` with root `npm run sync:style`. Contours come from `EXPO_PUBLIC_CONTOUR_TILE_URL`, from the worker's `contours` (Australia) source for a trail inside that archive's bounds and its `world` source for every other trail (`contourSourceFor` in `online-style-service.ts`) — the Australia archive returns empty tiles abroad.
- **Map theme**: the map follows the app theme (`useTheme().isDark`), not a setting of its own. Dark is a *night topo*, not a separate style: `src/services/night-style.ts` repaints every layer of the light style — Liberty online, `topo-style.json` offline — by colour role (areas inverted into a dark band, lines compressed so roads stay lighter than the ground, text lifted, halos darkened, hue kept), so forest, parks, water, paths and relief survive in dark mode. (It replaced OpenFreeMap's Dark-Matter `dark` style, which drew a near-black map with none of them.) Offline, the paint patch `scripts/topo-style-dark.json` (also synced by `npm run sync:style`) is merged over the repaint for the layers it does not suit — today only the contours, whose ink matches the online contour layers; a test asserts every id in it still exists in the template. Overlay cartography (tracks, marker/label ink, the fallback style) is per-theme in `features/map/map-style.ts` — `trackColors(theme)` / `mapInk(theme)` — and the theme is part of `mapRemountKey`, because swapping a live map's style object can kill the native renderer.
- **Storage**: trail content is read via `src/services/trail-loader.ts` — there is no `trails` SQLite table. Sources: bundled JSON assets (the seed), newer copies downloaded from R2, catalog-only trails, community routes, and user imports. SQLite (`expo-sqlite`) holds per-guide state, comments + outbox, favorites, and custom routes. Tile files live in `expo-file-system`.
- **Over-the-air trail data** (runbook: `docs/trail-data-updates.md`): `services/trail-data-updates.ts` fetches `{EXPO_PUBLIC_TILE_BASE_URL}/trails/v1/catalog.json` on launch/foreground (`hooks/useTrailDataUpdates`, throttled to 6 h; My Guides pull-to-refresh forces it) and downloads newer content-addressed trail files to `{documentDir}/trail-data/` (size + md5 + shape checked on a `.part` file before `state.json` names it; `state.json` itself is written to a temp file and renamed into place). The pure rules are `services/trail-catalog.ts`: a copy replaces another only when its `updatedAt` is strictly later, so a newer APK beats an older download and unpublished build data is never reverted. A downloaded copy of a bundled trail makes the sync `getTrailJson` return null (callers fall back to async `loadTrail`); use `getBundledTrailJson` only where stale data is fine. Catalog-only trails (`source: 'remote'`) are listed from the last catalog, downloaded on first open by `GuideProvider` (or the shared-plan screen), and registered with `isServerKnown` via `registerRemoteTrailIds`. An open guide keeps the data it opened with until the hiker taps Reload on the banner it shows once a newer copy is installed (`GuideContext` `dataUpdate`, compared by `trailDataVersion`, the md5; `GuideUpdateBanner`); Settings → Guide updates forces a check
- **Hiker waypoints** (`@lib/user-waypoints`): SQLite `user_waypoints` (schema v7, `db/user-waypoints-repo.ts`) holds both kinds; `state/user-waypoints-store.ts` mirrors a trail's rows and re-reads on every `SyncChange` with `userWaypoints: true`. `GuideProvider` places them into the trail (`placeUserWaypoints`) before direction is applied, so `trail` and `baseTrail` carry them and the map, list, profile, detail screen and planner need no special case. Writes go through `sync/waypoint-sync.ts` (`saveUserWaypoint`, `deleteUserWaypoint`, `reportUserWaypoint`): SQLite first, then for a shared one an outbox row (`waypoint` — a full replace, newest only — `waypoint-delete`, `waypoint-report`) that `comment-sync`'s drain sends; a shared → private edit deletes the server copy. A 410 on the `waypoint` PUT, or a tombstone pulled for one of this account's own, keeps the hiker's copy as a private waypoint (`keepAsPrivate`) rather than deleting the only record of the place. `pullTrail` pulls shared waypoints as a third channel (`sync_state.waypoints_synced_at`, every page), skipping any with a write still queued (one outbox read, the rows applied in one transaction). The waypoint detail screen says who added one, offers Edit (own) or Report (another hiker's shared one), and has no comments on a private one. `deleteTrailScopedRows` clears them with the guide
- **Community routes** (`c_…`, `TrailSource 'community'`): `services/community-routes.ts` caches `GET /v1/community/routes` in `{documentDir}/community/state.json`, refreshed alongside trail data (30-minute throttle, forced by pull-to-refresh), and downloads a route's `trailUrl` on first open with size, md5 and shape checks, and again when the list's md5 changes (owner edit, de-attribution). A list never deletes anything: it can be truncated, stale or briefly empty, so each downloaded route it leaves out is probed (`GET /v1/community/routes/:id`, no token, `no-store`, ≤ 20 per refresh) and only a 404 marks it `takenDown` — kept on the phone, shown as "No longer shared" in My Guides and the guide banner, cleared if a list names it again. Opening a route that 404s shows "This route is no longer shared" (no retry) and forces a list refresh. Long-press on a community card: About & report, Remove from this phone. Removing a route or the owner deleting it runs `services/local-trail-data.deleteLocalTrailData` (custom routes, favourites, waypoint_meta, comments/outbox/sync_state, plan, `plan-inputs-store`, direction, current-hike pin), the same cleanup an imported trail's delete runs. Pure rules in `community-catalog.ts` (`planCommunitySync`, `classifyCommunityProbe`); the client is `api/community.ts`. A route this phone knows — in the cached list or downloaded, a "No longer shared" one included — is server-known: every load and save of the state pushes the ids into `server-trails` (`registerCommunityTrailIds`), so it gets comment sync, the composer, plan sync and shared hiker waypoints like a bundled trail (the worker refuses new comments and shares on a hidden route with 403 `trail_not_live`, which the outbox marks failed; plans keep syncing). Comments go under the route's own `uw_` waypoint ids, `hw_` and `osm_` (`@lib/comment-targets`; `CommentsSection` offers no composer under any other id on a `c_` route). It has no curated descriptions, and borrows offline packs like an import (`offline-pack-resolver` asks `isCuratedTrailId`, not `isServerKnown`). The shared-plan screen downloads a plan's community route (`ensureCommunityRouteDownloaded`) as it does a catalog-only trail. A `u_` import is never server-known. A hidden route is never in the list or My Guides; its owner finds it under Settings → My shared routes (`features/community/useMySharedRoutes.ts`).
- **Custom routes** (`features/routes/`, SQLite `routes` + `route_points`): drawn on the map pane by tapping; a tap within 200 m of the track is a snap point (the nearest vertex's lat/lon and km), a farther one a sketch point (lat/lon only). Snap km are stored NOBO-absolute and stats (distance, ascent, descent) are denormalized onto the row. Both are only true of the track they were taken from, so `routes.track_key` (schema v8) records `routeTrackKey` of that track, and `GuideView` calls `routes-store.resnap` with the stored (NOBO) display track on every open: each route saved against another track — or with no key, every route from before v8 — is snapped again from its lat/lon (`resnapRoutePoints`, the builder's own `classifyTap` rule), its stats recomputed and written back, once per change of geometry. A snap point the redrawn track no longer passes becomes a sketch point where it was, and `routes.off_trail_points` counts it, so the Routes screen tells the hiker ("The trail data changed since this route was drawn; N points are no longer on the trail.").
- **Shared code**: `src/lib/` (repo root) modules imported via `@lib`. Currently used (as of 2026-10-23; `grep -rhoE "from '@lib/[a-z-]+'" mobile/src mobile/app` for the live list): comment-targets, comments-api-types, community-checks, community-types, contribution-licence, day-calculator, day-suggest, distance, elevation-axis, elevation-backfill, format-distance, gpx-import, map-glyphs, osm-poi, overpass-client, plan-alternates, plan-direction, plan-editor, plan-stop-issues, plan-suggest, plan-types, poi-dedup, poi-display, poi-enrichment, position-on-trail, region-detect, resupply-display, resupply-plan, route-breaks, text-links, track-geometry, trail-handoff, trail-poi-search, trail-regions, trail-reverse, trail-types, types, user-waypoints, water-carry-calculator, waypoint-glyphs, waypoint-taxonomy, xml-adapter-fxp. Every `src/lib` module is RN-safe: `gpx-parser`/`gpx-optimizer` no longer reach for `DOMParser` (mobile passes `fxpXmlAdapter`), and `gpx-import` avoids `crypto` entirely. jsdom stays out of `src/lib` — its adapter lives in `scripts/lib/xml-adapter-jsdom.ts`.
- **Navigation**: a single Expo Router Stack — "My Guides" list → per-trail guide (nested stack). No bottom tabs. Inside a guide, a segmented control switches three always-mounted panes: Map | Elevation | List (`src/features/guide/GuideView.tsx`).
- **State**: Zustand stores in `src/state/` (settings, downloads, favorites, identity, plans, trail-data, user-waypoints) plus per-guide React contexts. Per-trail pace and daily hours are in `features/plan/plan-inputs-store.ts`; the resupply selection and the zero days per resupply stop (`resupplyZeroDays`) are in the plan document (`state/plans-store.ts`), and `use-planned-resupply.ts` is the one source of "planned resupply" for the map, profile, list, detail screen and distance strip — `null` until a plan is made, and `null` means nothing is planned, never everything.
- **OSM points of interest**: bundled trails carry `pois` (slimmed by `build-mobile-trails.ts`), imported ones whatever the `.tracknotes.json` handoff brought, or what the on-phone search found: a GPX imported on the phone starts with none, and its map's layers sheet (shown for every `u_` guide, `features/import/can-search-pois.ts`) offers "Find places along this route" → `guide/[trailId]/find-pois`. That search (`features/import/poi-search.ts` + `use-poi-search.ts`) is never started by the app: the screen first shows the request count, a download range (`@lib/trail-poi-search` `planTrailPoiSearch`), the upload, the connection type (expo-network) and which public Overpass servers get the route outline. It runs the build's corridor queries one at a time, each tried on `INTERACTIVE_OVERPASS_ENDPOINTS` in turn (`createFallbackFetcher`), then the build's passes (`finishTrailPois`: noise → duplicates → city thinning → `slimPoi`) with `yieldToUi` between slices, and writes only `pois` into the import's file (`imported-trail-store.saveImportedTrailPois`, re-read first); the guide re-reads it through `GuideContext.reloadTrail`. Cancel, or every query failing, writes nothing; a partial result is saved and "Retry the missed areas" re-asks just those queries and saves the union. "Remove points of interest" deletes the key (back to never-searched). POIs are never waypoints: they are not in the plan calculators, the GPS distance strip or favorites, and `duplicateOf` entries are never drawn or listed (their OSM detail shows on the waypoint they duplicate instead). One global `poiFilter` in the settings store (master switch + six categories) drives every surface through `features/guide/use-visible-pois.ts`; the map's layers sheet edits it, and so do the planner's chips (`features/plan/PoiFilterChips.tsx`, on the Today screen and above the Plan screen's day splits) — the planner never keeps a filter of its own. Map markers are smaller, thin-ringed badges hidden below zoom 11; the List pane interleaves POI rows (an "OSM" pill) by km; the elevation profile draws hollow ticks only when zoomed to ≤ 60 km; the Today screen lists the day's visible POIs among its waypoints as OSM rows (km from the start, off-trail distance, opening hours) that never split a waypoint's leg (`today-plan` `todayPois`/`todayEntries`), and each Plan day card counts them ("Along the way (OSM)", `DaySplitList` `dayPoiSummary`) — still never in the calculators' figures; `guide/[trailId]/poi/[poiKey]` is the detail screen. A POI takes comments like a waypoint, filed under `poiCommentId` (the worker needs no change: the id is just another waypoint id on an allowed trail). Direction reversal mirrors POI km inside `@lib/trail-reverse`, so nothing on mobile special-cases it.

## Mobile Route Structure (`mobile/app/`)

- `_layout.tsx` — Root Stack (ThemeProvider, GestureHandlerRootView)
- `index.tsx` — "My Guides" home, a SectionList built by `features/guide/guide-sections.ts` over `@lib/trail-regions` (Hiking now, one section per country, Community, Imported) with a search box: bundled trails (download badges), community routes (Verified/Unverified or "No longer shared" pill; long-press for About & report and Remove from this phone) and imported ones ("Imported" badge, long-press to delete); ＋ header action picks a GPX; a pin on each card marks the trail being hiked now (settings store `currentTrailId`, rules in `features/guide/current-hike.ts`): it leads the list with a "Hiking now" pill, and a fresh launch pushes its guide over the list once (not when the launch was an incoming file)
- `settings.tsx` — App settings (units, display name, Linked browsers: mint a link code, list and revoke linked tokens; My shared routes)
- `my-shared-routes.tsx` — Every route this account shared (`listMyCommunityRoutes`, any status), the one place an owner sees a route hidden by the review, reports or a moderator (it leaves the public list, and with no `trailUrl` it cannot be a guide). Cards show the status pill (Verified/Unverified/Hidden), the `hiddenReason` line and the review summary, and expand in place to the description, credit, checks, review concerns, Delete (`deleteCommunityRoute` + `forgetCommunityRoute`; a 404 counts as deleted) and, for a live route, Open guide. `?id=` opens one route expanded. Reached from Settings and from the share screen's 409
- `share-route.tsx` — Modal: share an imported trail to the community (runs `@lib/community-checks` once per trail and re-checks only `checkCommunityMetadata` as the hiker types; region may be "Not specified / several"; the server's 409/429 text is shown, and a 409 carrying `existingId` (the hiker's own earlier route) adds "View my shared routes", opening that route on `my-shared-routes`; CC0 confirmation required). Reached from an imported guide's header and its My Guides long-press menu
- `community-route.tsx` — (root-level, `?id=<c_…>`, so it never waits on the trail download) A community route's status (incl. "No longer shared"), description and credit, Report (non-owners, once the detail has loaded), Delete for the owner, and Remove from this phone
- `import.tsx` — Modal: review a picked GPX (name, counts, warnings) then save it as a guide
- `guide/[trailId]/_layout.tsx` — Per-trail guide stack, wrapped in `GuideProvider` + `GuidePositionProvider`; header actions for Routes / Plan / Offline maps / Settings
- `guide/[trailId]/index.tsx` — Guide home: renders `GuideView` (Map | Elevation | List panes)
- `guide/[trailId]/downloads.tsx` — Offline maps: download/delete tile packs
- `guide/[trailId]/plan.tsx` — Day planner over the saved plan, measured along the route it walks (`features/plan/use-plan-route.ts`: the guide's `baseTrail` with the plan's alternates spliced in, direction applied; the resupply screen, the shared-plan screen and the plan-at-a-glance surfaces use the same route). Name, start date, section, pace and hours/day sit behind one summary row and the header ⚙ (`PlanSettingsSheet`), so the screen opens on the plan rather than its inputs; the Next days card starts folded. A `StopIssuesCard` under the summary row lists the stops a data update left without a place (`@lib/plan-stop-issues`, judged after the guide's `refreshStopKms`; rows and the day-card warning from `features/plan/stop-issues.ts`), each with a Remove button and the shared hint (ticking an unplaced stop's own place in Stops moves it there); the shared-plan screen shows it read-only. Then: summary stats, Next days card (ranked alternative plans for the next K nights from the GPS km / last stop), OSM POI filter chips (`PoiFilterChips`, the guide's one `poiFilter`), day cards with dates, rest days and an "Along the way (OSM)" count line (each POI counted on one day: a stop's km belongs to the day ending there) plus a "Not planned yet" tail, Stops section (overnight candidates, each row showing the distance, ascent and descent from the stop before it — `plan-stops.stopLegs`, so the figures reset at every ticked stop — with a card where each alternate branches off (Take this alternate / Stay on the main route) and where a taken one rejoins, an `OffTrailBadge` on places off the route, OSM services strips and a "You are here" divider the screen scrolls to on a fix; a ticked stop expands to nights / note / booked), water carries. Under the settings summary row sits a labelled **Resupply** row (`ResupplyEntryRow`: "5 stops · longest 7 days · 2 to decide", from `resupply-planner` `resupplyEntryText` over `plan-adapters` `computeResupplyPlan`) that opens the resupply screen with the section as route params; it replaced the Resupply section and its "Choose stops" link at the foot of the screen
- `guide/[trailId]/today.tsx` — Today's plan: the planned day dated today (the phone's local date) from the stop slept at to tonight's, every waypoint between with the distance, ascent and descent from the row before and the totals so far, and among them the OSM POIs the guide's POI filter shows (filter chips under the summary), measured on the route as planned (`features/plan/today-plan.ts` + `use-today-plan.ts`, over `use-plan-glance`). A rest day says where; no start date, a date outside the plan or one in the "not planned yet" tail shows nothing for today. The guide header's `calendar-today` button (`TodayHeaderButton`) appears only while today has a planned day or rest day. Every row with an id opens its waypoint, a taken alternate's places included
- `guide/[trailId]/day.tsx` — One day of the plan, opened by tapping a day card on the Plan screen (`DaySplitList` `onDayPress`): the Today screen's list (`features/plan/DayWaypointList.tsx`, shared by both) for that day. The route params (`today-plan` `dayRouteParams`) carry the day as the card showed it and the Plan screen's section (dropped by `sectionOnRoute` once it no longer fits the route); the screen rebuilds the plan's days over that section (`use-plan-glance` `usePlanBasis` + `planGlance`) and shows the one that starts where the opened day did (`currentPlanDay` — the stop slept at survives renumbering and re-dating, where a date or day number would land on another stretch), or says the stretch from there is "not planned yet" or no longer in the plan; the rows are rebuilt on `use-plan-route`'s trail
- `guide/[trailId]/find-pois.tsx` — Modal: the on-phone OpenStreetMap search for an import (above): estimate and connection first, then progress with Cancel, the result by category with a retry of missed areas, Remove, and the ODbL credit (`credits.POI_SEARCH_CREDIT`)
- `guide/[trailId]/resupply.tsx` — The resupply planner, a regular stack screen titled "Resupply" (from the Plan screen's Resupply row, a resupply waypoint's "Open the resupply planner" link, or `tracknotes://guide/<id>/resupply`). Laid out like the hiker's planning spreadsheet (`features/plan/ResupplyPlanner.tsx` over the pure view-model `resupply-planner.ts`): a summary on top (`summariseResupplyPlan`: stops, longest leg, most climb, longest carry, heaviest food, walking km, total days incl. zero days) and a one-line, editable list of the hiker's inputs (hours/day and pace in `WalkingInputsCard`, food per day and long-carry days in `PlanThresholdsCard`, inside `PlanSettingsSheet`; all `plan-inputs-store`); then start → leg → stop → … → end, each leg just above the stop it arrives at. A decision group (the places from one turn-off) is a radio list plus "None – carry through" (`chooseResupplyOption`), a group of one a Yes/No switch, and a group with more than one place still ticked (the every-option default included) says "Not decided yet" (`resupplyGroupChoice`). Each option shows `storeLabel` (nothing when unknown), its access (`accessSummary`, or "On trail"), "Accepts boxes" and the description's first sentence, the rest behind More. Each leg shows walked km with `legSideTripText`, rides not walked (`legRidesText`), ascent/descent, days, food and a Long carry badge — no arrival days, and no camp plan is passed to `computeResupplyLegs` (the plan's rest days and the zero days would double-count). A chosen stop has a zero-days stepper in half days (`setResupplyZeroDays`, passed to the legs as `zeroDays`). Every edit goes through `plans-store.apply`, built from the document when it runs (`chooseResupplyEditor`, `zeroDaysStepEditor`; the device-local legacy selection is the base only while the document has none). Clear choices drops the selection back to "no plan made", which turns the highlights off. Groups outside the Plan screen's section (route params `startKm`/`endKm`/`startName`/`endName`) are dimmed and get no leg
- `plan/[shareId].tsx` — Shared plan opened from `tracknotes://plan/<shareId>`: read-only days, "Save as my plan"
- `guide/[trailId]/routes.tsx` — Saved custom routes (built on the map pane)
- `guide/[trailId]/waypoint/[waypointId].tsx` — Waypoint detail + offline-first comments, a "Show on map" button (leaves the place in `features/guide/map-target.ts` and dismisses to the guide, which takes it on focus and calls `GuideFocusContext`'s `showOnMap`: Map pane, centred on the waypoint's own position at zoom ≥ 14, with its `offTrailPath` dotted in the main track's red until the next tap on the map) (+ a collapsed "From OpenStreetMap" section when a POI duplicates the waypoint), a "Stop here" toggle backed by the plans store with a `StopContextCard` under it (the day that ends here and the one that leaves from here — "If you stop here" before a camp/hut/town is a stop, via `plan-glance` `stopContextIfStopped`; "View whole plan" opens `PlanGlanceSheet`), and for a resupply-family waypoint its access line, a `Plan resupply here` / `Remove from resupply plan` toggle — the resupply screen's decision (`resupply-planner` `waypointResupplyEditor`): planning picks the place in its turn-off's group, removing the group's chosen place carries the group through, and a lone place is Yes/No — with an "Open the resupply planner" link under it and a `Planned resupply stop` banner when planned. It opens an alternate's waypoints as well as the main route's (`plan/waypoint-alternates.ts` `findGuideWaypoint`: main route first, then each alternate's by id), and gives the place a `WaypointAlternateCard` for each alternate it bears on (`waypointAlternates`): the one it is on (km along it), one that leaves or rejoins the main route here, or a taken one that bypasses it. Each card names where the alternate leaves and rejoins the main route (a link to that junction's place within 250 m), whether the plan takes it, and offers `Take this alternate` / `Stay on the main route` through `setPlanAlternate` (naming any taken alternate it would drop). A place on a taken alternate is on the route as planned: it can be a stop, and `TripCard` measures to it along that route (`along`, from `routeKmOfFix`); on an untaken one it has neither. `TripCard` ("From your location", given the place as `place`) adds its walk in (`placeWalk`) to the trip through `addPlaceWalks` and times the whole as one Naismith estimate, as the planner does, so its distance, climb and ETA include the walk; the line under them says how much is the walk and what it climbs, or that its climb is not known (no `offTrailAscentM`/`offTrailDescentM`) — never "↑ 0 m"; a ride or a straight-line distance is only stated
- `guide/[trailId]/waypoint-edit.tsx` — Modal: add (`?lat=&lon=`, from a long-press on the map or the map's ＋ button at the GPS fix) or edit (`?id=`) a hiker waypoint: name, type chips, note, "Only me" / "Everyone" (sharing only on server-known trails; asks for a display name on first share), "Use my location", Delete. Saves through `sync/waypoint-sync`
- `guide/[trailId]/poi/[poiKey].tsx` — OSM point-of-interest detail (`poiKey` is `@lib/poi-display`'s `poiRouteKey`, `type-id`): "Show on map", tag lines, scheme-guarded links, OSM/Maps deep links, "Report a problem on OpenStreetMap" (`poiNoteUrl`, no OSM account needed), attribution, and the waypoint screen's comments block (`features/comments/CommentsSection`) under `poiCommentId`. No favorites

## Mobile Source Structure (`mobile/src/`)

Feature-sliced: UI lives with its feature, not in a global components dir.

- `features/` — one dir per feature, each with colocated `__tests__/`:
  - `guide/` — GuideView shell, waypoint list pane (waypoint + POI rows; a `Resupply` pill and a `Planned` chip once a resupply plan exists), contexts (GuideContext, GuidePositionContext), direction toggle, distance strip (a `Next resupply` chip while a plan exists, never falling back to an unplanned town), `use-visible-pois.ts`, `OffTrailBadge.tsx` ("1.2 km off trail", an outlined pill in the theme's `offTrail` teal: the one way the list pane, POI rows, the Today screen and the planner's Stops rows mark a place the route does not reach; figures from `waypoint-detail` `placeOffTrailMeters`, cached per trail object — a turn-off's own `offTrailKm`, else straight to the line, badged past `PLACE_OFF_TRAIL_M` (50 m); the waypoint screen shows the same figure as an "Off the route" stat)
  - `map/` — MapPane, GuideMap, map styles/geojson, waypoint + POI icons (`assets/map-icons/*.png`, rasterised by `mobile/scripts/build-map-icons.mjs` from the shapes in `@lib/map-glyphs` — edit the shapes there, then run it with ImageMagick, or `npx -y -p @resvg/resvg-js node scripts/build-map-icons.mjs <names>` where it is missing; Node 22.18+ for the type-stripped import), POI layers sheet, track legend, error boundary; planned resupply stops are ringed in `colors.resupplyPlanned` (planned beats favourite)
  - `elevation/` — Skia elevation profile (axis, geometry, LOD, POI ticks, planned-resupply markers). Both axes are the hiker's: the y-axis is an elevation window (`EleWindow`, 0 m to just above the trail's high point by default) that never refits to the km window — a vertical pinch or the pane's stretch/flatten buttons zoom it, a horizontal pinch zooms km

# Build scripts (`scripts/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session.
`CLAUDE.md` keeps the everyday commands, the rules and a pointer here;
every `npm run` script is in `package.json` and described below;
keep this file in step with the code it describes.

- `build-trails.ts` - Generates static trail pages + `public/data/generated/*.json` from GPX/JSON data;
  the geometry work lives in `@lib/trail-ingest` (`buildTrail`) — this script only supplies the file-system pieces (config, CalTopo GeoJSON, CSV fallback, climate, curated descriptions, waypoint-id registry) and writes the output
  Where its waypoints come from is `lib/trail-waypoint-sources.ts` (`readTrailGpx`, `findGpxFile`, `findGeojsonFile`, `parseCaltopoGeojson`, `resolveTrailWaypoints`: the GPX's `<wpt>`s, typed and described from the nearest same-named CalTopo marker, with the CSV fallback), kept apart from the script because importing the script runs a build:
  what `resolveTrailWaypoints` returns is, in order, what `assignWaypointIds` is handed, and `lib/waypoint-editor/build-parity.test.ts` holds the waypoint editor's own prediction of that list to it
- `build-app.ts` - `npm run build:app`: a production Vite build of the web pages into `dist-app/` (gitignored) for the Playwright smoke suite (`web-ui.md`, "Testing").
  Vite's `publicDir` copy is off; it copies `public/` itself minus `data/tiles/` (the local tile packs, tens of GB), and stops with the rebuild command when `public/data/generated/index.json` or a trail's generated page is missing.
  `npm run build` (Vercel's) is unchanged.
- `build-mobile-trails.ts` - Builds mobile-optimized trail JSON (reduced points, truncated precision).
  A trail with route breaks is simplified one stretch at a time, so Douglas-Peucker cannot drop a break's boundary points and cut the corner across the water;
  `index` is re-anchored to the result, `displayIndex` is re-anchored the same way, because `displayPoints` is thinned here too: the web copy is no longer a fixed ~3,000 points (see `trail-ingest.ts`'s tolerance ceiling), so the phone clamps it to the same `TARGET_POINTS` budget as `points` — a line no coarser than the array it already ships, and no finer.
  Every point of both arrays also gets `cumAscent`/`cumDescent`, measured on the full-resolution track *before* thinning (`annotateCumulativeElevation`, skipping the step into each break) and rounded to whole metres: thinning keeps the shape of the line, not its ups and downs, so without them the phone's plans, ETAs and route stats under-counted climb by 14-35%.
  `processTrail` is exported and `main()` guarded so this is testable.
  `index.json` records each file's `md5`/`bytes`, and a trail's `updatedAt`/`dataVersion` move only when its md5 changes (the previous index is read back), because `updatedAt` is what the app orders over-the-air copies by.
  It exits 1, writing nothing, when its input is incomplete (`missingInputProblem`): no generated index, a listed trail with no generated file, or a trail the app bundles that the generated index lacks — what `build:trails` leaves when it fails a trail — each of which used to drop the trail from the app's index with a `SKIP` line and exit 0
- `check-data-unchanged.ts` - `npm run check:data-unchanged`: does this tree build the same trail data as a baseline? `public/data/generated/` is gitignored, so git cannot show what a change to `trail-ingest`/`gpx-parser`/`track-simplify` did to it.
  `-- --baseline` builds `origin/main` as last fetched (`git fetch origin` first for today's; `--ref <ref>` for another) in a temporary `git worktree`, borrowing this checkout's `node_modules` when the lockfiles match and running `npm ci` there otherwise, and saves the outputs to a snapshot in the system temp directory (one per checkout; `--snapshot <dir>` to choose);
  `--baseline --current` snapshots this tree instead, for a check before you start editing.
  A plain run rebuilds this tree in place (`sync:te-araroa`, `build:trails`, `build:mobile-trails`, as CI's trail-data job does; `--no-build` compares what is on disk) and compares every file in `public/data/generated/`, `mobile/assets/trails/`, the generated `src/web/trails/<id>/` pages and `data/waypoint-ids.json`.
  After a build it skips gitignored files in `public/data/generated/` and `src/web/trails/<id>/` older than that build — leftovers of a renamed or removed trail, which a fresh baseline worktree never has and which would otherwise read as added;
  `--no-build` compares everything on disk.
  It prints each differing file with the keys that changed (two levels deep) and how arrays moved (lengths; for arrays of `{ id }` records, which ids came, went or changed), and exits 1 on any difference, 2 when a build fails.
  Ignored are only the clock fields, listed in `lib/data-diff.ts`: a generated trail's `dataUpdatedAt` and the app index's `updatedAt`/`dataVersion` (its `md5` is still compared).
  Two consecutive builds of one tree are byte-identical, these included; they move only with the build clock, when a trail's data differs from the app's committed copy — so a baseline at a ref whose app data is not rebuilt would otherwise differ in every such trail
- **Contour zoom tiers** (`tile-pipeline.ts`: `CONTOUR_TIERS`, `contourTierLayer`, `contourTierFilter`, `contourTippecanoeArgs`, `renameContourTiers`) - which elevations appear at which zoom (100 m lines from z9, 50 m from z10, 20 m from z12, 10 m from z13), shared by the world build, the per-trail offline packs and the experiment harness (and by the retired Australia build, below). tippecanoe's `-L {"file","layer"}` object has **no `minzoom` key**: every archive built before 2026-10 passed one and had it silently ignored, so each z9–z12 tile carried every 10 m contour, blew its byte budget, and `--drop-smallest-as-needed` (whose threshold applies to a whole zoom level, set by its densest tile) emptied it — Mt Sonder's live world z9 tile kept one 100 m line — while the Australia archive's `--minimum-detail=4` quantised what survived onto a 16×16 grid: the "jagged when zoomed out" contours.
  So each tier is read as its own tippecanoe layer (`contour_z9`…), a `-j` feature filter admits it from its minzoom (`$zoom`), and tile-join `-R` folds the layers back into the one served `contour` layer (`renameContourTiers`) — the world build's batch and shard joins do it in passing, the other builds add one tile-join pass.
  The tippecanoe quality bundle (`CONTOUR_TIPPECANOE_DEFAULTS`: simplification 2 at z9–14, minimum detail 7, 1 MB tiles) is defined once there too;
  the per-trail packs used to tile with the pre-decision-gate flags.
  Re-tiering is a tippecanoe-only change: `--merge-only` re-runs, no cell rebuild, wherever the tier files survive.
  The world build deletes its tiers (`--clean-work`), so for it a re-tier is a full rebuild from the DEM.
  A world batch's `.done` marker records the tippecanoe release and `contourSettingsHash(WORLD_CONTOUR_OPTIONS)` (the options object the merge itself tiles with) with its cells, so a batch tiled with other settings or by another release is re-tiled, never reused, and `--join-batches` refuses it. tippecanoe is pinned to felt's 2.79.0 (`TIPPECANOE_VERSION`, `bootstrap.sh`'s `TIPPECANOE_REF`): `checkDependencies` refuses any other for the world archive (`TIPPECANOE_ANY_VERSION=1` overrides) and warns for the rest.
  The Australia archive (`contours/australia.pmtiles`, Geoscience Australia 1" SRTM DEM-S, ~24 h build by the now-deleted `build-contours-australia.ts`) was retired in #228: the same z14 tiles at seven Australian trails were near-identical to the world archive's (elevations within 10–30 m, world 3–15% more line length because DEM-S is hydrologically smoothed, no visible canopy artefacts).
  It stays in R2 as a frozen public download (last built 2026-10-23, 13.5 GB, CC BY 4.0) and is no longer served or rebuilt
- `build-contours-world.ts` - Builds world contour shards from Copernicus GLO-30 DEM, `--join` converts the shard mbtiles to `.pmtiles` in parallel (tile-join integrity-checks mbtiles inputs on one core, hours at world size, but not pmtiles ones), tile-joins them to world.mbtiles and converts that to a validated world.pmtiles;
  `--join` takes only the real shards' `world_<shard>.mbtiles` (`isWorldShardFile`), never the `world_custom.mbtiles` a `--bbox` or `--cell` test build leaves in the same dir.
  `--batches-only --batch I,J` tiles only those batches of a shard (0-based), so separate processes can tile one shard's batches in parallel and the shard's own merge reuses them (design decisions: the runbook, `contours/docs/world-contours-remote-build.md`).
  Each batch is tiled under a per-process temp name and renamed into place before its `.done` marker is written, so a killed or concurrent run never leaves a half-written batch under the real name.
  `--batches-only` writes `batches.json` (the batch count, each batch's `.done` label and the settings) once every batch of the shard is built, by whichever `--batch` process finishes last;
  `--join-batches` refuses to run without it, and refuses a missing or extra batch, a marker that differs from the manifest, or other settings (`joinBatchesProblems`).
  `main()` is guarded so the module imports without building;
  `build-contours-world.test.ts` covers the pure parts — argument parsing (`--batch`, `--cells-only`, `--batches-only`), byte-capped batching, the batch `.done` labels and when a batch is reused, the `--join-batches` manifest check, the shard names `--join` takes, and `--join` reusing a shard conversion only when it is newer than its shard
- `fetch-dem-copernicus.ts` - Downloads Copernicus GLO-30 DEM tiles (global, anonymous, per bbox/cells/shard)
- `contour-experiment.ts` - Contour quality experiment harness: settings-matrix builds + side-by-side compare viewer (`npm run experiment:contours`).
  `baseline` is built from `CONTOUR_TIPPECANOE_DEFAULTS`, so it cannot drift from the builds;
  `untiered` and `legacy-simp-14` reproduce the archives as deployed before the tier fix, `visvalingam` tries tippecanoe's other simplifier.
  The compare page draws the real `topo-style.json` contour layers (round joins included), so what you judge is what the app draws
- `lib/world-grid.ts` - Global 2° cell grid, shard partition, Copernicus tile naming
- `lib/trail-data-catalog.ts` - Pure helpers shared by `build-mobile-trails.ts` and `publish-trail-data.ts`: file digests, the `index.json` merge rule (keep `updatedAt` while the md5 is unchanged), the R2 catalog shape, content-addressed keys, validation, and the upload plan
- `lib/xml-adapter-jsdom.ts` - jsdom `XmlAdapter` for `parseGpx` (kept out of `src/lib` so jsdom never enters the mobile bundle)
- `remote/` - Remote-machine world build (runbook: `contours/docs/world-contours-remote-build.md`): bootstrap (`bootstrap.sh` for Ubuntu/Debian, `bootstrap-al2023.sh` for Amazon Linux 2023), `rclone-from-token.sh` (the `[r2]` remote derived from one Cloudflare API token: key id = token id, secret = SHA-256 of the token), the unattended drivers `drive-world.sh` (DEM fetch with retries, a `--cells-only` lane and a pool of shard merges side by side) and `finish-world.sh` (cleanup, `--join`, validation, upload), the single-shard driver `run-shard.sh`, `status.sh`, `upload-world.sh`
- `sync-te-araroa.ts` - `npm run sync:te-araroa`: copies the published Te Araroa route out of the `te-araroa-data` package into `data/trails/te_araroa/` (never hand-edit it; fix it upstream).
  It copies the file `trail.json` names as `gpxFile` from the package's `out/`.
  `lib/te-araroa-package.ts` holds the checks, and each failure names its fix: the package must be in this checkout's own `node_modules` at the commit `package-lock.json` pins (`npm ci`) — Node's resolution walks up, so a worktree under `.claude/worktrees/` without it used to copy the main checkout's copy, another commit, and exit 0 — and `build:trails` refuses a synced GPX that is missing or differs from the installed package's (`npm run sync:te-araroa`), since the gitignored copy outlives the install it came from
- `build-region-shapes.ts` - `npm run build:region-shapes`: regenerates `src/lib/region-shapes.ts` (coarse Natural Earth outlines for `@lib/region-detect`) from the regions in `src/lib/trail-regions.ts`.
  It reads Natural Earth's `master` branch, unpinned (the commit behind the committed file was not recorded), so pin one when you next regenerate
- `fetch-climate.ts` - `npm run fetch:climate`: fetches historical climate data for trail locations (Open-Meteo) into each trail's `climate.json`.
  `npm run build` (Vercel's) runs it in its default mode, which skips every trail that already has a `climate.json`, so a build fetches nothing while the committed files are complete.
  It exits 1 when a location's fetch fails (the trail's file is left unchanged) and when a trail's own files cannot be read or written (a malformed `trail.json`), and carries on with the other trails either way.
  `--check` fetches nothing and exits 1 when a trail's `climate.json` is missing or does not answer every `climateLocations` entry (`staleClimateLocations`: one added, moved or re-elevated, or data for one no longer configured), which `build` does not catch since it only fills trails with no file;
  CI's `trail-data` job runs it, and the fix is `npm run fetch:climate -- --changed`.
- `fetch-pois.ts` - Fetches OSM POIs along each trail corridor (`npm run fetch:pois [trail-id]`) through `@lib/osm-poi`, `@lib/overpass-client` and `@lib/poi-enrichment` — the `src/lib` port of the `gpx-tools` search, which the phone runs too, held to that library byte for byte by `scripts/osm-poi-parity.test.ts`.
  Reads track geometry from `public/data/generated/{id}.json` (so `build:trails` must have run) and writes the results to `data/trails/<dir>/pois.json` — in the repo, where a rebuild cannot wipe them.
  `--endpoint <url>` / `OVERPASS_ENDPOINT` and `--timeout <seconds>` pick the Overpass instance;
  mirrors come and go, so try them in turn: `overpass.private.coffee` served the Australian trails (2026-09-08, `--timeout 120`), but by 2026-09-30 it timed out from a cloud session, where `overpass-api.de` reset the connection and `overpass.kumi.systems` timed out too.
  What answered there was `--endpoint https://maps.mail.ru/osm/tools/overpass/api/interpreter`, which drops any query past about 60 s, so it wants small cheap ones: `--max-vertices 60 --timeout 55` (or 150/120 for a lighter trail).
  A run that loses chunks merges what succeeded into the existing file instead of replacing it (so a whole-trail run can never ship a hole), prints which chunks failed and exits 1 — re-run it until no chunk fails (how the CDT's file was built);
  `--force-replace` writes the partial result as-is.
  An empty answer counts as a lost chunk when the existing `pois.json` has POIs (other than `rejected` ones) inside that query's corridor (`guardEmptyAnswers`): on 2026-11-11 `overpass-api.de` answered the whole Shikoku corridor, sent as one query, HTTP 200 with no elements and no error remark, which the run took for a clean whole-trail fetch and replaced 1,206 POIs with none, exit 0;
  when every chunk is lost that way the fetch fails and writes nothing.
  Those empty answers tracked query size and server state: two days later the same server still answered the one-query corridor empty and returned it complete in 8 chunks (`--max-vertices 10 --timeout 120`), so re-run with a smaller `--max-vertices`, not the same query again.
  The guard cannot tell that fault from a corridor whose stored POIs really were all deleted or retagged in OSM, and such a chunk fails on every run: `--force-replace` writes the fetch without them once it is the only chunk still failing;
  when it is the trail's only chunk the fetch fails before any write, `--force-replace` or not, and those entries have to be removed from `pois.json` by hand.
  An empty answer is caught chunk by chunk, but a short one passes that guard: Shikoku's 2026-10-06 file (from `maps.mail.ru`) lacked Kamiyama's long-mapped POIs at km 56–59 until the next refresh.
  So a whole-trail replace writes nothing for that trail and exits 1 (`shrinkRefusal`, gated by `checksShrink`) when the fetch lacks more than half the stored POIs of any 5 km band holding at least 10 (`SHRINK_BAND_KM`, `MIN_BAND_POIS`, `MAX_BAND_LOSS_FRACTION`), or has more than 30% fewer POIs overall and at least 5 fewer (`MAX_SHRINK_FRACTION`, `MIN_SHRINK_DROP`);
  the band check is the one that catches a regional loss: the truncated Shikoku file had only 21% fewer POIs than the complete one (1206 against 1525) but lacked 16 of the 23 at km 55–60, and none of the committed re-fetches would have tripped it.
  `rejected` keys are left out of both checks;
  re-run, against another mirror or with a smaller `--max-vertices`, or pass `--allow-shrink` when the POIs really are gone from OSM.
  `--force-replace` is checked too, leaving out the stored POIs inside its failed chunks' areas (the loss it accepts), so a short answer elsewhere in that run is still refused;
  a merge (`--from-km`/`--to-km`, or failed chunks) never shrinks the file and is not checked, and `--allow-shrink` has no effect there or with `--dry-run` or `--reposition`.
  A loss spread thinly under both thresholds still passes, so check which km a new file's POIs span before committing it.
  A POI's km is measured against the track as fetched, so a later track edit (or placement fix) leaves it stale;
  `--reposition` re-places the POIs already in `pois.json` on the current track with no Overpass query (exactly a fetch's placement, so an unchanged trail comes out byte-identical; with `--dry-run` it only reports what would move or drop, and writes nothing), and `build-trails` fails when any stored km or category differs from that placement (`misplacedPois`, about 12 s across all trails) — it writes the trail's generated JSON first, so `--reposition` (which reads the track from it) sees the edited track;
  any windowed fetch (merged, or the first file for a trail with no `pois.json` yet) and any partial fetch's merge are re-placed on the whole route for the same reason (`placesOnWholeRoute`) — the AAWT's Blue Waterholes POIs sat at km 790 of 688 and the SOBO view listed them at km 0.
  On 2026-10-06 `overpass.private.coffee` answered again (`--timeout 120`, Shikoku in one 182 s query), but its data lagged: the same day `maps.mail.ru` (`--max-vertices 60 --timeout 55`) returned a 2026-09-21 survey of central Tokushima that it lacked
- `fetch-access.ts` - Finds where each off-route waypoint is walked to from (`npm run fetch:access <trail-id>`): every main-route waypoint at least `--min-distance` (150 m) off the line — not turn-offs, not ones within 200 m of one of the trail's side trips (the side trip is the way there, and OSM may lack it), and not ones whose source already gives `offTrailKm` (and, with the same exclusions, every waypoint the main route did not match — an off-trail row or an alternate's own — that is off an **alternate** by `--min-distance` up to the trail's match radius, `waypointMaxDistance`, 500 m by default, and nearer it than the main route) — is routed over OSM's walkable ways (`isWalkableWay`: no motorways, nothing `foot=no`/`access=private`) with `@lib/access-routing`, heights from Copernicus GLO-30 read by HTTP range requests (`scripts/lib/dem-sampler.ts`, the `geotiff` devDependency; behind a proxy run with `NODE_USE_ENV_PROXY=1`).
  Only a tile the bucket answers 404 for is open ocean;
  any other failure to read heights fails that query like an Overpass error (retried, previous entry kept, exit 1), never a flat walk.
  Nearby places share one Overpass query (boxes ≤ 10 km across: bigger ones over Japanese cities drew HTTP 500s), and every answer is cached in the gitignored `data/osm-ways-cache/`, so a change to the routing re-runs from disk (`--refresh` re-downloads; a box cached longer than `--max-cache-age`, 90 days, is fetched again).
  A 429 (or a 503 with `Retry-After`) waits as long as the mirror asks, up to 5 minutes, before the next query.
  Failed queries get three more passes a minute apart;
  `--only <ids>` re-runs what a run lost.
  A waypoint the build merged near-duplicates into (`dedupeWaypoints`, its `mergedIds`) gives every twin the same entry, or the merge would keep the twin without one on the next build;
  nothing else reads `mergedIds` (the app looks comments and descriptions up by a row's own id), which is why the waypoint editor lists each merged-away twin for deleting;
  on such a trail a second fetch-and-build round can still move a survivor, so re-run until `fetch-access` changes nothing.
  A place off an alternate is routed to that alternate's line (`alternateRoute`: km from its `points[0]`, the branch point) and its entry names the alternate as `variant`, with `junctionKm`/`nearestKm` along it;
  an alternate whose name another shares is never routed to, since the entry names it.
  Writes `data/trails/<dir>/access.json` and prints each place's km before → after;
  a failed query keeps the place's previous entry and exits 1, so re-run until it exits 0.
  Same mirror caveats as `fetch-pois.ts`: on 2026-10-11 `overpass.private.coffee` 500'd most queries and `maps.mail.ru` (`--timeout 55`) served them
- `fetch-font-glyphs.ts` - `npm run fetch:fonts`: downloads the map label font glyphs (`.pbf` ranges) the offline style uses, skipping files already on disk;
  it exits 1 when any file failed, so re-run it until it exits 0.
- `build-tiles.ts` - `npm run build:tiles [-- --trail <id>]`: builds map tiles for offline use: a Protomaps vector base map plus contour lines from the Copernicus GLO-30 DEM — everywhere, Australia included, so a pack draws the same lines as the online `world` source (Australian packs were cut from SRTM until #228).
  Fetch the DEM first with `fetch-dem-copernicus.ts --bbox …`;
  a build with tiles missing fails and prints the exact command.
  Composited by a custom MapLibre style.
  Ready-made providers were rejected (Feb 2026): OpenFreeMap/Protomaps have no contours, OpenTopoMap is raster-only, MapTiler On-Prem and Thunderforest's offline tier are too expensive for a non-commercial project, and Mapbox Outdoors would mean leaving MapLibre.
  Hillshade was prototyped and dropped: little gain on a phone screen, nearly double the pack size (~60 MB more for Bibbulmun) and Android raster compositing bugs
- `check-install.mjs` - Compares each `package-lock.json` (root, `mobile/`, `workers/comments-api/`, `contours/worker/`) with what npm recorded installing (`node_modules/.package-lock.json`) and with each package's own folder (its `package.json` present, at the pinned version), and names the packages that are missing, at another version, or from another commit of a git dependency.
  Optional packages count only when their `os`/`cpu`/`libc` name this machine, so a missing native binary for this platform (`@rolldown/binding-linux-x64-gnu`) is caught and the other platforms' binaries are not expected.
  `npm run check` runs it first (`check:install`): a checkout that pulled a dependency change without reinstalling fails its suites for reasons that are not in the code, and a stale `te-araroa-data` rebuilds different trail data.
  Node built-ins only, so it runs against a broken install; pass directory names to check only those.
  `npm run check` then runs `check:web` (`tsc`, Vitest, ESLint, `format:check`), `check:workers` (the comments API suite and both Workers' `tsc`) and `check:mobile` (Jest, `tsc`, ESLint).
  It does not run CI's trail-data job, which rebuilds the trail data and fails if the committed output differs, because that is a slow full build.
  Its local equivalent is `npm run check:data-unchanged` (`check-data-unchanged.ts`, above; `-- --baseline` first): it runs the same rebuild in place and lists what moved, so after a change to the build or the source data, commit the rebuilt files it leaves and check `git status`.
- `e2e-tile-check.mjs` - Probes the deployed tile infrastructure through the URLs the app uses (`mobile/eas.json`): contour worker health and tiles, and an offline pack for **every trail in `mobile/assets/trails/index.json`** (manifest lists `base.mbtiles` and `contours.mbtiles`, each object present at the manifest size).
  `--base` (every full run, and `check:tile-packs`) reads `sources.base` from the app tile worker's `/health` (`https://tiles.tracknotes.info`, `BASEMAP_TILE_URL` to override): the archive must be there, reach z15 and span the world (`BASEMAP_UPLOADED` in the script is true since the planet upload of 2026-11-06; set false, a missing worker or archive only warns).
  `npm run check:tile-packs` runs the pack and tier checks and that one;
  the `tile-packs` workflow runs it when the bundled trail list (or the script) changes, so a new trail fails CI until its pack is built (`build:tiles --trail <id>`) and uploaded (`upload:tiles <id>`).
  Weekly (and on a manual run) the workflow runs every check instead (`node scripts/e2e-tile-check.mjs`), so the contour Worker's `/health`, tile decode, the z14/z15 tiles and the alias are watched too; all of it is read-only GETs to the public hosts, with no credentials.
  `--tiered` (`npm run check:tiered`, and every full run) checks the contour tiers are live: the worker's Mt Sonder z9 tile (`world` and `contours`, 9/444/290) holds only 100 m lines at ~1,500 features, and every z9 tile of every pack's `contours.mbtiles` holds only 100 m lines, with at least one contour feature per pack (a pack whose tiers were never folded into `contour` draws nothing).
  `--alias` (`npm run check:contours-alias`, and every full run; not part of `--tiered`, because the `tile-packs` workflow runs that on pull requests, before a worker change is deployed) checks that `contours` really is the alias of `world` (#228), which the density check cannot tell, since the retired Australia archive was tiered too: `/health`'s `sources.contours.archive.key` must be `contours/world.pmtiles` (the alias deploy is live), and `/contours/…` and `/world/…` must serve byte-identical tiles through the edge for Mt Sonder z9 and a Kosciuszko z12 (the purge of the edge-cached `/contours/*` URLs took effect).
  The pack z9 tiles are read four packs at a time with HTTP Range requests through `scripts/lib/http-mbtiles.mjs`, a read-only SQLite walker for every mbtiles layout (plain `tiles`; `map`/`images` with `images` keyed by `tile_id` as tippecanoe writes it or by `(zoom_level, tile_id)` as tile-join does, which every tiered pack is) that waits out the data domain's 429s and retries a 200 for up to 75 s (the edge now and then ignores the Range on the packs too big for its cache, CDT and Te Araroa — the tile-packs failure of 2026-10-30), closing each such body unread, and decoded by `scripts/lib/mvt-contours.mjs`, both Node built-ins only.
  Every request of the pack and tier checks (the manifests, the pack check's 16-byte probe, the range reads) goes through `fetchWithRetries` in the same module, which retries a network error (a bare `fetch failed`), a body cut off mid-read (`terminated`), an attempt that passes its 30 s timeout, or a 5xx, up to four times on one budget shared by all of them (5 s doubling, 75 s of waits), and a 429 up to six times on its own; it never retries a 404 or other 4xx: the weekly run failed every other week on `fetch failed` for a few packs at once (#368).
  A `Retry-After` (on a 429 or a 5xx) is honoured up to a minute, and every retried answer's body is closed unread.
  An unreadable manifest is a failure of the tier check, not a pack it skips; a manifest the host answers 404 for is left to the pack check.
  The tier check's reads share one 6-minute budget (`TIERED_PACKS_BUDGET_MS`): past it no read waits to retry, so a brownout ends in a failure in the RESULT block rather than the workflow's `timeout-minutes` (15) killing the job before it prints anything.
  A read that still fails names the host, path and byte range of the request, the number of attempts and, through `readZoomTiles`, what it was reading (the schema, the z9 index, or tile `9/x/y (TMS)`), so a failure reads `could not read contours.mbtiles z9: tile 9/x/y (TMS): range request to <host> <path> bytes a-b request failed after 5 attempts: fetch failed (<cause>)`.
  It passed on 2026-10-24 once the #135 rebuild was live, so `check:tile-packs` (and with it the weekly workflow) now includes it
- `upload-tiles.sh` - `npm run upload:tiles [id...]`: publishes built packs to R2, manifest last.
  A manifest file absent locally is skipped when the bucket already serves its content-addressed key at the manifest's size, so a pack that changed one file can be republished without downloading the rest.
  Every published manifest is then purged from Cloudflare's edge (`CLOUDFLARE_API_TOKEN` with Cache Purge on the zone): the edge has served `manifest.json` days past its `max-age`, and the app fetches the plain URL, so an unpurged republish reaches no phone.
  No `CLOUDFLARE_API_TOKEN` refuses the whole run before anything is uploaded (`require_purge_token`);
  a purge that fails anyway fails the script after the upload;
  `--no-purge` opts out when purging by hand.
  The app fetches the manifest with a per-minute `?m=` (`tile-service.ts` `manifestUrl`, like the trail catalog), so the purge is a backup for current builds and still the only path for older ones
- `cleanup-superseded-tiles.ts` - `npm run cleanup:tiles`: the pack objects at old content-addressed keys that `upload-tiles.sh` leaves behind.
  Lists the bucket with rclone (`RCLONE_REMOTE`; wrangler cannot list), reads each pack prefix's live `manifest.json` from the bucket, and plans to delete every `.mbtiles` directly under the prefix that the manifest references neither by `key` nor by plain `name` (pre-content-addressing app builds, and a current build that cannot read the manifest, download the plain name).

  Never touches a prefix whose manifest it cannot read, sub-directories, other files or other prefixes.
  Dry run by default, `--delete` deletes;
  `--world-build` does the same over `contours/world-build/`, refusing unless `contours/world.pmtiles` is newer than everything under it;
  `--trail-data` does it over `trails/v1/` (`planTrailDataCleanup`): the trail files the live `catalog.json` does not list by `key`, once the catalog is past the grace, refusing a catalog it cannot read or that lists no trails;
  with `--delete` it re-reads the live catalog before each trail file (`listedTrailKeys`) and keeps one a publish has listed again meanwhile.

- `publish-trail-data.ts` - Over-the-air trail data (`npm run publish:trail-data`; runbook: `docs/trail-data-updates.md`).
  Checks `mobile/assets/trails/index.json` matches its files byte for byte, then uploads each file to R2 at content-addressed `trails/v1/<id>.<md5[0..12]>.json` (only keys the live catalog lacks) and `trails/v1/catalog.json` **last**.
  `--dry-run` prints the plan, `--check` exits 1 when the live catalog differs, `--all` re-uploads everything.
  Two guards against a publish from a stale checkout: it refuses to roll a trail's live `updatedAt` back, and the catalog records the `sourceCommit` it was published from, so a checkout whose HEAD does not descend from it is refused too (`--force` overrides both; without git it warns and continues).
  Dropping a trail the live catalog has is refused unless that id is named with `--remove <id>` (or `--force`), because a trail missing from `index.json` is usually a build that failed for it, not a decision.
  `--hold <id>` (`holdTrails`) leaves one trail exactly as it is live — the live entry for a live trail (never re-uploaded, even with `--all`), nothing for one not live yet — so a new trail can wait while the rest publishes;
  `--check` takes it too.

- `lib/waypoint-editor/` - The local waypoint editor's server half (runbook: `docs/waypoint-editor.md`): `vite-plugin.ts` mounts its API on the dev server only and checks every request itself (`requestRefusal`: a loopback address, a loopback `Host`, which is what refuses DNS rebinding, no foreign `Origin`, and a custom header on writes), since Vite's host check is not there to rely on (a plugin's middleware runs before it under Vite 6, and `server.allowedHosts: true` turns it off under any version);
  it runs Rebuild (`build:trails` then `build:mobile-trails`), reporting the ids minted or retired and every warning line of the build (all of stderr, where the build puts its warnings, the id-minting ones included), and refuses saves while one runs, with the state on `globalThis` and in a lock file so that a dev-server restart or a second dev server sees it;
  `vite.config.ts` imports it, so it imports only types and Node built-ins and loads the modules below per request with `ssrLoadModule`: an edit to them, or to `src/lib`, does not restart the dev server;
  `trail-state.ts` joins the last build's waypoints back to their `<wpt>` (`claimSpans`) by what the build's id matching keeps an id on without question: the exact coordinates, the name the build shows and the type it gives, registry entry first (so a saved move, rename or retype is still found), then the waypoint as built;
  each `<wpt>` is claimed for one id (the passes of a revisited place share theirs), so a waypoint whose `<wpt>` is gone shows as deleted even when another waypoint's `<wpt>` stands on the same coordinates (the CDT's towns hitched from one pass);
  `<wpt>`s may share a position, and an add, a move or a rename is refused only when it would put two there under one build name (`namesakeAt`: of one type they are twins the join and the build's id matching cannot tell apart, and of different types a pending key, which is the position and name, would be one for both), so a deleted waypoint added back on its exact position under its name and type is joined to its id at once, beside whatever stands there;
  that restores the id and not the `<wpt>`, and the delete's and the add's notes say what an add does not write back (`addBackNote`, `restoreGapsNote`: the `<extensions>` the build reads the off-trail fields from, the old `<ele>`, a CalTopo marker, a `descriptions.json` entry);
  it applies a save to the GPX, the CalTopo export, `descriptions.json`, `data/waypoint-ids.json` and, for a renamed or deleted revisited place, trail.json's `revisitedWaypoints`, with every write and the answer computed before any is made, and the files then replaced together or not at all (`commitWrites`: a temporary file beside each, renamed over it, and the ones already replaced put back if a later one fails);
  it lists each id in a built waypoint's `mergedIds` (a near-duplicate the build merged away, `dedupeWaypoints`) as a row of its own, joined to its `<wpt>` through its registry entry, deletable through the same delete and renamable (which takes it out of the merge under the id it has), with its position, type and description locked;
  `mergesWith` repeats the build's single-linkage rule over the waypoints of one merge, to say which duplicates the next build will list again when one is deleted or renamed;
  it lists a `<wpt>` nothing was claimed for as pending, under a `new:` key (a hash of its name and position), until the next build mints its id;
  one with a live registry entry exactly on it that the last build does not list (the committed registry ahead of the locally built data: a pull without a rebuild) is listed under that id, locked (`notBuilt`), and twins that nothing tells apart are locked under their ids and not listed as pending;
  a pending waypoint goes through the same `saveWaypointEdit` as any other, but every edit stays in its `<wpt>` (the description in its `<desc>`), nothing is written to the registry or `descriptions.json`, the refusals are an add's, and the answer carries it under its new key;
  `resolveSourceType` reproduces how `build-trails.ts` types a `<wpt>` (nearest same-named CalTopo marker, then `<type>`, then the name), so a type change edits the source that decides it and the registry entry's `type` together;
  it is the editor's own implementation, so `build-parity.test.ts` runs it beside the build's (`sourceIdInputs` against `readTrailGpx` and `resolveTrailWaypoints`) over every committed trail directory: the two must give the same `<wpt>`s in the same order with the same name, type and position, from the same GPX and CalTopo files, and `assignWaypointIds` over that list must leave `data/waypoint-ids.json` byte for byte as committed;
  a change to the build's typing, name cleaning or GPX reading that the editor does not follow fails there, instead of letting an "ids kept" check pass an edit the build would re-key;
  Te Araroa is skipped, visibly, where its GPX has not been materialised (`npm run sync:te-araroa`; CI's web-tests job does not run it, the trail-data job does), and the suite takes about 18 s, most of it the build's parser reading the large GPX files;
  every move, rename and type change, of a built or a pending waypoint, is checked the same way before anything is written: the type the build resolves for the edited `<wpt>` must be the one meant, a CalTopo marker that types another `<wpt>` too is never edited (and no edit may make two `<wpt>`s share one), and the build's own `assignWaypointIds`, run on a copy of the registry over every `<wpt>` before and after, must keep every id, this waypoint's included when it has one;
  an add and a delete run the same id check, which tells a built waypoint that would lose its id from a pending one that would be handed a built one's (a delete beside it: refused until a rebuild gives the pending one its own), and from a pending one that would only be minted another new id (two of one type on one position take theirs in file order: noted, not refused);
  the same run gives the id the next build will mint for (or hand back to) a pending waypoint, which the save's notes name, and refuses an add or a pending edit that the build would hand the id of a waypoint deleted since the last build (its entry is not retired until a build runs), unless it is that waypoint restored under its name;
  `elevation.ts` looks up the elevation for the `<ele>` of an added or moved `<wpt>`, a pending one's move included (the build never reads it; the source GPX stays complete): the route's own, interpolated between the track points either side, when the position is within the build's match radius of the main route (`waypointMaxDistance`, 500 m by default; never across a route break, never from a track without elevations), otherwise Copernicus GLO-30 through `lib/dem-sampler.ts` with an 8 s limit, otherwise nothing;
  the DEM is an injected `DemSource`, imported on first use, so tests never touch the network and starting the dev server loads no `geotiff`;
  the plugin awaits the lookup (`lookupWaypointElevation`) and hands the result to the save, which stays synchronous, and a lookup that fails or times out never fails a save;
  `sources.ts` reads the GPX's `<wpt>`s as the build's parser does (one in a comment is not a waypoint, `<name>` and `<type>` are taken untrimmed, a missing or unusable `lat`/`lon` throws as it stops the build) and holds the byte-preserving edits (a `<wpt>` attribute, `<name>`, `<desc>`, `<type>` or `<ele>` in place, a `<desc>` added or removed, a `<wpt>` inserted or removed in the file's own style, line ending and coordinate padding, a JSON value spliced in place, a CalTopo feature or `folderId` spliced in or out, a name in a JSON array of strings replaced in place or taken out, a JSON file rewritten only when its layout reproduces exactly).
- `upload-descriptions.ts` - PUTs curated waypoint descriptions to the comments API (`npm run upload:descriptions`, admin token in `$TRACKNOTES_ADMIN_TOKEN`; `--dry-run` prints the requests).
  Every PUT says `source: 'upload'`, and the plan (`planDescriptionSync`, one function for the dry run and the real one) reads each synced row's `source` to say what a PUT or withdrawal replaces:
  text an earlier upload sent is listed plainly (`replaces uploaded text`), which is every routine edit;
  a live edit from `admin-descriptions.html` that the file does not match, or a live clear of an id the file lists, is marked `!` and ends the run with a warning (a `::warning::` annotation in Actions; the exit code is unchanged).
  The run itself is `runDescriptionUpload` in `lib/description-upload.ts`, with the network and the output passed in (its tests run it against the worker's PUT semantics in memory);
  the script reads the arguments and the files.
  A real run never replaces what the reader of its plan was not shown.
  A dry run writes the live edits and clears it marked `!` with `--record-live <file>` (one line of JSON, `{"version":1,"live":{"<trailId>":{"<waypointId>":"<updatedAt>"}}}`, ids and timestamps that passed their patterns only), and a real run undoes a live edit or clear only when `--acknowledged-live <file>` names it at the version the API still holds;
  any other is not sent (its line is marked `✗`), so a run given no file undoes none.
  Every PUT carries the `updatedAt` the run read for the row as `ifUpdatedAt` (`null` for no row), a "mark as uploaded" one included, so the API answers 409 `description_conflict` to a write over a row that changed between the read and the PUT, and the script reports what the row now holds and does not retry.
  After either refusal the other rows are still sent and the run exits 2, with an `::error::` annotation in Actions;
  exit 1 is a run that failed and stopped (arguments, a malformed file or acknowledged set, any other API error), and 0 is everything sent, warnings or not.
  Text from the API is printed quoted, on a line the script starts, so it cannot forge an annotation.
  A live edit the file already matches is re-sent unchanged to mark it uploaded (`adoptions`; the API leaves `updated_at` alone), so a later change to that entry is an ordinary edit;
  the summary line counts those, and the workflow's "nothing to upload" check greps that line, so the two change together.
  Both refusals need a worker that records `source` and honours `ifUpdatedAt`, which the descriptions read states (`writeFeatures`, `guardsDescriptionWrites`).
  Against a worker that does not say so, nothing can be called a live edit and no precondition holds: a dry run prints its plan with the warning "Live edits not checked", and a real run sends nothing and exits 1, unless `--allow-unchecked-live` is given (a run by hand that accepts overwriting any live edit unseen; the workflow never passes it)
  The *Upload waypoint descriptions* workflow runs it after a merge that changes a `descriptions.json`, once approved (`docs/deploys.md`), as *Publish trail data* runs `publish-trail-data.ts`:
  its `plan` job runs the dry run with `--record-live` and passes the line on as a job output (after checking it is one line of that alphabet, under 500 kB), and its `upload` job writes it to a file from an environment variable and passes `--acknowledged-live`.
